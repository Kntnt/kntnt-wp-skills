## What 006–011 are for, in one line each

- **006** — the client decides whether the Extractor withheld a define's value by looking at the value, which the Extractor's own `docs/define-disclosure.md` says a reader MUST NOT do; the operator is consequently told a define was withheld when the server in fact disclosed it as `null`, and is given the same one-line remedy whether the reason was `secret` (leave it alone) or `not_allow_listed` (the site operator can opt it in). **Read its "Why this matters" third paragraph before believing it recovers the legitimately-null case** — it deliberately does not, and says why.
- **009** — `extract-transfer` is told to wait inside one blocking invocation and return once with a verdict. On **both** production runs it returned without one, and on the second it had backgrounded the poll first, so the poll outlived the agent and would have reported to nobody. The written close-out for a verdict-less return is `DELETE`; only a manual check of the job stopped a healthy 2.5-hour extraction being cancelled. The instruction is not the problem — a boundary a model can cross cheaply will be crossed, so the fix moves the boundary.
- **010** — the companion guard, and the smaller one: on any `FAILED` **or absent** verdict, re-query `GET /extractions/{id}` and let the job's own state outrank the subagent's claim. An absent verdict carries no information about the job, yet today it routes onto the branch that cancels it. One sentence of ordering; it has now saved a run twice.
- **011** — `unseal.py` reported `files_written: 48578` while 48,552 distinct files landed: 26 NFC/NFD pairs that Linux keeps apart and APFS merges, 18 of them with differing sizes. **The defect is the silent count** — the helper counts what it wrote, never what landed, so it cannot notice a collision it caused. Impact was bounded this time and the plan says so.
- **008** — the Extractor's unreleased work makes `consume` take the per-job tick lock and answer `409 kntnt_extractor_locked` when it is held, with "the caller simply retries" as the intended handling. This client has no handling and its own rule that an unconsumed job is always `FAILED`, so a narrow lock contention turns a finished multi-hour run into a failed verdict. **The race is narrow and the plan says so** — the data is never at risk, since download and unseal both precede the consume. Found during release preparation, not by the original audit.
- **007** — the client's copy of the restricted-path pattern family is stale against the widening the Extractor's plan 016 makes, and `grep -rn "kntnt_extractor_restricted_path"` over this repository's runtime surface returns nothing at all. Once the server widens, a site carrying a `wp-config.old` or an `id_ed25519` fails the whole create at submission on an error code the client has never seen. The pattern widening is one file; the handling is the part that matters, because the mirror is allowed to go stale again by design.

## Dependency notes

**004 has the only hard dependency in this set: it must not begin until 001 is merged.** Raising the ceiling to 7 is the act of declaring this client correct against API version 7 — the version where the Extractor's define allow-list starts returning `null` for defines this client classifies as portable. Without 001 that declaration is false, and a clone against a version-7 Extractor writes `define('NAME', null);` into `wp-config.php`. 004's own STOP conditions restate this.

Plans 001, 002, 003 and 005 are independent of each other and touch disjoint files; they can be executed in any order, or in parallel by separate agents.

Soft couplings worth knowing:

- **002 before 003's step 4.** Plan 003's report enumerates the widened stall window as one of the degradations an older Extractor causes. If 003 lands first, that bullet describes behaviour that does not exist yet.
- **Settle the Extractor's `capabilities` array before executing 003.** The Extractor side's plan 014 adds a named-capability list to `GET /status`. It does not change 003's code — the plumbing is identical either way — but it does change the shape of 003's step 4 report, from a hand-maintained "below version N implies feature F" list to a mechanical one. Executing 003 first means writing that step twice.
- **005's step 3 is optional and may be skipped.** It uses the Extractor's forthcoming terminal-job listing; if that contract is unsettled when 005 runs, skip step 3 and note the skip here. Steps 1, 2, 4 and 5 stand alone.
- **001 before the Extractor's allow-list reaches production**, not merely before 004. The client-side fix has no coordination cost and stands on its own.

None of the five touch the adaptation family (host-limit raising, budget halving, the attempt counter, the floor), so none are blocked by rule R1 in `~/Projects/kntnt-transfer-engine-open-work.md`.

## Findings considered and rejected

- **`strict: false` is silently ignored by an Extractor that predates it.** Not a finding. The degradation is deliberate and documented: `CHANGELOG.md`'s `[Unreleased]` entry states that `strict` "defaults to today's hard fail on an older Extractor that ignores the member, and the new fields are additive, so the verified API-version ceiling stays ≤ 6". The behaviour is safe — the old failure mode, not a new one. What remains is only that the operator is not told the mitigation is inert on their host, which is one bullet in plan 003's report step, not a plan of its own.
- **Raising the API-version floor from `≥ 2`.** Considered and deliberately not planned. Raising it to reflect what the client actually assumes would refuse production (`safeteam.se`, Extractor 0.4.0, API version 5) until a coordinated release and a manual wp-admin install have happened. That is the repository owner's operational decision, not a cleanup; plan 003 makes it an informed one and explicitly leaves the literal alone. **Settled 2026-08-16**: the decision is taken *after* the production install, not before — until production runs the released Extractor, a raised floor is a bar against the only production site this client has. Not a plan yet; revisit once the install is done.
- **`tests/test_api_version_ceiling_consistency.py` asserts only that strings appear in Markdown files.** Real, and worth knowing — every assertion in it is a regex over a document, so nothing binds a *behaviour*. But the suite is honest about being an anti-drift binding for prose, and the gap it leaves is exactly what plan 003 closes by making the version a value rather than a sentence. Not worth a separate plan.
- **`docs/poll-discipline.md` binds the stall-window phrase as a hard-coded string rather than deriving it from `scripts/poll_extraction.py`'s constant**, unlike the cadence and timeout phrases beside it. Real but trivial; folded into plan 002 step 5 rather than carried as its own finding.
- **The `--yes` dependency gate, the cache-hit rules, the credential-splitting rule, and the exclusion-set assembly.** Audited and found sound. Each is carefully specified, each has a consistency suite or a unit suite behind it, and none showed drift from its ADR.
