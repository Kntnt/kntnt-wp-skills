# pull

Refresh an existing local DDEV copy of a production WordPress site. `pull` and its sibling `clone` run **one shared transfer engine** — discovery, extraction on production, download, verification, remote cleanup, import, and localisation — and differ only at the bookends. A clone is a pull with no baseline; a pull always has one, so only the delta moves: it takes a rollback backup of the local database first, diffs production against the stored baseline so only new and changed files are extracted, and re-applies the local state — the inactive plugin set, the object-cache drop-in — afterwards. Every run begins with a **health check** that fails early and cheaply, then walks the operator through a series of **gates** whose recommendations come from the deterministic helpers; `--yes` runs the whole thing unattended and prints a full record. A **risk warning** is always emitted before the destructive local steps.

All relative paths in this document are relative to the directory containing this SKILL.md (the skill directory), regardless of where the skill is installed. This skill ships no helpers of its own: the transfer engine belongs to `clone`, the site `pull` refreshes was created by one, and so its deterministic helpers are `../clone/scripts/`, its phase instructions `../clone/roles/`, and its one local template `../clone/templates/`. `../mkwp/scripts/classify.py` is the classifier the `mkwp` skill owns and ships (issue #51).

Read the [specification](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/spec.md), the [glossary](https://github.com/Kntnt/kntnt-wp-skills/blob/main/CONTEXT.md) (its terms are used verbatim below), and the [implementation notes](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/implementation-notes.md) (the invocation-level literals) alongside this file whenever you can reach them — inside a plugin install they sit at the plugin root, two levels above this file. Where a literal here and the spec diverge, the spec wins. Nothing below depends on having read them: this document carries every value and rule the run needs.

If the arguments are `help`, `--help`, or `-h`: if the file `../../scripts/help.py` exists relative to this skill's directory (plugin install), run `uv run` on it with the argument `pull` and emit its output verbatim as Markdown, then stop. ## How the engine works

**Control channel.** Production is reached **solely** through the [Kntnt Extractor](https://github.com/Kntnt/kntnt-extractor) plugin's REST API on the live site — never SSH ([ADR-0016](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0016-kntnt-extractor-replaces-novamira-as-control-channel.md)). It is reached over HTTPS, authenticated as a real WordPress user via an Application Password (HTTP basic auth); that user's own capabilities bound what any call can reach. Authorisation is a **flat two-capability gate** — `kntnt_extractor_operate` is the on-switch and `manage_options` authorises the data; a user with one but not the other reaches nothing. The surface is fixed and minimal: `GET /status` (the unauthenticated API-version handshake), `GET /environment`, `GET /tables`, `GET /files`, `POST /extractions`, `GET /extractions`, `GET /extractions/{id}`, `POST /extractions/{id}/consume`, and `DELETE /extractions/{id}`, plus the `manage_options`-only `GET /audit-log`. There is no arbitrary PHP or WP-CLI execution on production and no SSH — the plugin owns the outside-docroot extraction, the per-segment sealing, the one-time download link, and the TTL cleanup, so the engine generates no shell script, handles no passphrase, and stages nothing in the docroot ([ADR-0017](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0017-discovery-over-extractor-rest-two-phase.md)). Never deactivate or delete Kntnt Extractor on production; it is the control channel. The skills **pin Extractor to API version ≥ 2 and ≤ 7** via `GET /status`: an older install is refused with a precise upgrade instruction, and a newer one — whose artifact shape this client has not been verified against — stops for the operator rather than risking a silent mis-reassembly.

**Credentials.** The Application Password's home is a documented convention, never something you have to be told anew each run, and its value never enters your own context — every authenticated call resolves it itself, inside that call's own subshell. Primary source: the macOS Keychain, service `kntnt-extractor-app-password`, account `<wp-user>@<host>`, retrieved with `security find-generic-password -s kntnt-extractor-app-password -a <user>@<host> -w` — always inside a subshell (e.g. `curl -u "<user>:$(security find-generic-password -s kntnt-extractor-app-password -a <user>@<host> -w)"`), never echoed, never printed, never interpolated into logged output. Portable fallback for non-macOS hosts: the environment variable `KNTNT_EXTRACTOR_APP_PASSWORD`. **Precedence:** the Keychain item wins when it exists on macOS; otherwise fall back to the environment variable. The health check (step 1, below) resolves and verifies this credential once; every later call you make yourself, and every role's task envelope, carries a `credential` **reference** — `{ "type": "keychain", "service": ..., "account": ... }` or `{ "type": "env", "name": ... }` — resolved by the calling code, never the password's value. **Splitting the account name: on the LAST `@`, never the first.** The account's first component is the WordPress `user_login`, which is very often itself an email address — `thomas@kntnt.com@safeteam.se` is a real, valid account name — so the host is everything after the final `@` and the `user_login` is everything before it. Splitting on the first `@` yields the user `thomas`, who does not exist, and an unknown login authenticates as nobody without ever reporting an error. The `user_login` is the value shown in **Users → Profile → Username** in wp-admin, and `GET /status` reports it back as `authenticated_as` (step 2, below); it is never the display name and never necessarily the email address.

**Cache-busting.** Every Extractor request URL carries a **unique** `_cb=<value>` query parameter — a timestamp plus randomness is enough, e.g. `_cb=$(date +%s)-$RANDOM` — appended with `?` when the URL carries no query string yet and with `&` when it already does. The paged `GET /files` loop is the one call that already has a query string (`?cursor=<opaque>`), so its buster is appended with `&`: `GET /files?cursor=<opaque>&_cb=<unique>`. This is not cosmetic. An Extractor older than the no-cache fix sends no `Cache-Control` on any response WordPress considers anonymous — which includes every refusal whose credentials failed to resolve to a user — so a page cache or CDN in front of production can store that refusal against the URL and replay it to every later call, correct credentials included, until the cache is purged. The buster makes each call its own cache key, so no stale entry can answer it, and it doubles as the cheap proof: a request that succeeds with a fresh `_cb` and fails without one was being answered by a cache.

**Cache interference.** An authenticated response carrying a cache-hit header is not an answer — it is evidence that something between you and WordPress is replying instead of WordPress. Capture the headers on every Extractor call (`curl -sS -D "<scratchpad>/headers.txt"`) and inspect them for `x-litespeed-cache: hit`, `cf-cache-status: HIT`, `x-cache: HIT`, `x-proxy-cache: HIT`, or a non-zero `age:`. On any of those, **stop** with the loud, specific diagnostic — *"Production served a CACHED response to an authenticated Extractor call (`<header>` on `<endpoint>`). Nothing read from production this run can be trusted. Upgrade Kntnt Extractor to the release that marks its REST responses uncacheable, or exclude `/wp-json/kntnt-extractor/` from the page cache, then re-run."* — and never fold a cached body into discovery, a diff, a selection, or a verdict. Never treat a cache hit as a transport hiccup to retry past: the retry hits the same cache key.

**The deterministic helper seam.** Every computation that needs neither production nor DDEV is done by a helper script under `../clone/scripts/`, invoked with `uv run` and fed JSON on stdin — all but one: `classify.py` is owned and shipped by the `mkwp` skill, at `../mkwp/scripts/classify.py`, because `mkwp` derives its own directory name from it and a skill must carry what it drives (issue #51). A pull refreshes a copy some earlier clone created, so reaching into `clone` for the engine is the dependency this skill already has; §1's preflight confirms both siblings are installed before a run leans on them. **Never compute a diff, a classification, a resolved plan, an extraction selection, an unseal, or a dump verdict by hand** — the model orchestrates gates and REST calls, the helpers decide the shapes ([ADR-0005](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0005-decision-backbone-gates-and-layered-defaults.md)). The seam is:

- `../clone/scripts/discovery.py` — assembles the one canonical discovery document from the four Extractor sources (`{ environment, tables, files, bootstrap }`).
- `../clone/scripts/bootstrap_parse.py` — parses the reassembled bootstrap extraction's `.sql` into the row-level signals (attachment metadata, entity counts, mass-send scan) the `environment`/`tables`/`files` surface cannot supply.
- `../mkwp/scripts/classify.py` — turns that document into the table split, the define classes, the flagged blobs, the thumbnail exclude-set, and the derived project and directory names.
- `../clone/scripts/resolve_plan.py` — resolves the ordered decision list over the layered defaults (`resolve`), and reduces an accepted plan back to the saved plan (`save`).
- `../clone/scripts/build_exclusions.py` — the single deterministic assembler of the **resolved exclusion set**: unions its canonical `ALWAYS_EXCLUDED` constant (the configuration file and its credential-bearing backup/swap/variant siblings, `.env` files anywhere in the tree, root-level SQL dumps and key material, drop-ins, logs, the known cache-plugin and backup-tool trees, the Extractor's own transfer-staging directories, upgrade dirs, and the whole WordPress core tree — `wp-admin/`, `wp-includes/`, and the root core PHP files) with the decision-gated thumbnail, blob, and media exclusions, so the baseline diff and the selection are fed one byte-identical set — never a hand-assembled list (issue #35).
- `../clone/scripts/filter_manifest.py` — restricts production's unfiltered `GET /files` walk to the resolved exclusion scope, locally, so the exclusion set never travels to production (issue #18).
- `../clone/scripts/baseline_diff.py` — diffs production's current (locally-filtered) manifest against the stored baseline and returns the new/changed set to extract and the production-deleted set the deletion gate draws from.
- `../clone/scripts/build_selection.py` — turns the resolved table split and file set into the `{ tables, tables_structure_only, files }` a `POST /extractions` submits, refusing an overlapping or empty selection locally (platform constraint 1).
- `../clone/scripts/unseal.py` — generates the run's ephemeral X25519 key pair (`keygen`) and opens a downloaded `KNTNTEXT` sealed container into the importable `.sql` and its files (`unseal`).
- `../clone/scripts/dump_sanity.py` — verdicts the reassembled dump against the discovered prefix before the import.
- `../clone/scripts/wpconfig_block.py` — writes the skills' marked block into `wp-config.php` and removes the scaffold `define()`/`$table_prefix` collisions it supersedes, computing the collision set dynamically (the portable defines plus `DISABLE_WP_CRON` ∩ whatever the scaffold shipped) rather than from a hard-coded name list (issue #42).

The only production-side template that remains is the local capture mu-plugin `../clone/templates/kntnt-wp-skills-mailpit.php`, dropped into the **local** copy when the mail decision resolves to capture — it never travels over the control channel.

**Run modes.** Interactive walks each gate. `--yes` accepts every recommendation, never pauses, and prints the full decided-and-done record. **Replay** engages automatically when a saved plan exists: interactive collapses to a single *Replay the saved plan?* gate, `--yes` replays silently — except the mass-send valve, which re-surfaces the mail gate even on a silent replay when a freshly-poised campaign would otherwise be masked ([ADR-0009](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0009-live-mail-default-with-mass-send-valve.md)).

**The gate shape.** Every decision is a **recommendation** behind an accept-or-override gate — *"Recommended: X. Accept? [Y/n]"*. `Y` accepts; `n` reveals the alternatives. Even multi-valued decisions take this shape. The recommendation is whatever `../clone/scripts/resolve_plan.py` resolved for that decision; a declined gate records the operator's answer, which the resolver layers above the recommendation.

**Persistent config.** Two per-project files at **the local project root** — the site directory `pull` is run from/on, defined once in [CONTEXT.md](https://github.com/Kntnt/kntnt-wp-skills/blob/main/CONTEXT.md): the saved plan `.kntnt-wp-skills.json` (settled per-site answers, committed, all keys optional) and the derived, gitignored `.kntnt-wp-skills/` (baseline manifest `last-sync.json`, rollback backups, trash). The saved plan stores **decisions, never computed lists**, so nothing in it goes stale. `pull` always operates inside the already-existing site directory, so the bare relative paths below already resolve to the local project root; `clone`, by contrast, walks its gates before that directory exists, so its own save (its §4, after the scaffold) writes the directory-qualified `<directory_name>/.kntnt-wp-skills.json` instead.

**Role execution.** Five phases — `discovery-classify` (Sonnet, low reasoning effort), `extract-submit` (Sonnet, low), `extract-transfer` (Sonnet, medium), `manifest-baseline-diff` (Haiku, low), and `thumbnail-smoke-test` (Haiku, low) — are each written once as a **role file** under `../clone/roles/`, so the REST round-trip logs, curl/download output, and thumbnail-regeneration warning spam they produce stay out of this agent's own context wherever a separate one exists to hold them — and out of every context, wherever it does not (see *Tier 3 is slower, not louder*, below). Run every role by the first of these three tiers your environment supports:

1. **Claude Code with this plugin installed.** Delegate the phase to its pinned subagent — `kntnt-wp-skills:discovery-classify`, `kntnt-wp-skills:extract-submit`, `kntnt-wp-skills:extract-transfer`, `kntnt-wp-skills:manifest-baseline-diff`, `kntnt-wp-skills:thumbnail-smoke-test` — via the Task tool, exactly as before. Each of those definitions carries the model and reasoning effort named above and reads the very same role file.
2. **Any other harness that can spawn a subagent or a background task.** Spawn one per role and give it `../clone/roles/<name>.md` as its whole instruction set, together with the task envelope that file's *Inputs* section names.
3. **Neither.** Execute each role file's instructions yourself, in the order this document prescribes, and apply its evidence-block format to your own notes.

The tier decides who runs a phase and whose context absorbs it, never what the phase does or what it must produce. Everything else — the health check, every gate, the risk warning, plan resolve, the wp-config edits, and the final report — stays here: a role runs once against a compact JSON task envelope and can never ask the operator anything. Each role writes any large payload (raw discovery JSON, the manifest, the reassembled dump) to a scratchpad file and returns only a short summary, the file paths, and its **evidence block** — exit codes, artifact paths with their SHA256, row/file counts, and a `DONE`/`FAILED` marker. **A result missing its evidence block is treated as `FAILED`, whatever its prose claims** — under tier 3 too, where the result is your own notes and skipping the block costs nothing at the time and everything afterwards. Verification stays deterministic, never a second LLM call: before trusting a role's result, re-run the one or two cheap checks its evidence block names — the dump-sanity verdict on the reassembled `.sql`, a `wp db check` exit code, or similar.

**Tier 3 is slower, not louder.** Every noisy step routes its full output to a log file under the run's scratchpad and prints only a compact summary, whichever tier runs it: `../clone/scripts/wp_quiet.py` for the thumbnail regeneration and the search-index rebuild, `../clone/scripts/smoke_test.py --log <path>` for the verify phase, and `../clone/scripts/poll_extraction.py --log <path>` for the extraction poll. An inline run therefore costs wall-clock time and a strictly sequential order — never a flooded context, and never a step whose output nobody kept.

## 1. Health check

Mandatory step 0 of the engine, before any heavy work. On any failure, abort with a precise remediation message — never a stack trace.

1. **Verify dependencies.** Before any production call, confirm every local and production dependency this run needs — local first, since it is cheaper to fail before ever reaching production. On the first missing dependency, stop immediately: report what to install or fix, where to get it, and the exact command to re-run once done. The agent never installs system software itself; where a fix is safely agent-runnable (e.g. `brew install jq`), offer to run it as its own accept-or-override gate before re-checking, rather than assuming consent. This gate is never auto-accepted under `--yes` — an unattended run has no operator present to consent to installing system software, so `--yes` aborts with the remediation message instead of running the fix.
   - **Siblings.** This skill ships no engine of its own, so confirm before anything else that the two it reaches into are installed beside it: `../clone/scripts/discovery.py` and `../clone/roles/thumbnail-smoke-test.md` (the transfer engine and its phase instructions, which `clone` owns) and `../mkwp/scripts/classify.py` (the classifier). A plugin install always has them; a standalone install that received only this skill would otherwise fail deep inside discovery instead of here. If any is missing, stop with the remediation: install the `clone` and `mkwp` skills beside this one — `npx skills add Kntnt/kntnt-wp-skills` for the standalone channel, or `/plugin install kntnt-wp-skills@kntnt-wp-skills`, which always installs every skill.
   - **Local.** `ddev` is on `PATH` and its container backend actually responds — `ddev version` exits zero, and a cheap Docker/Colima liveness probe (`docker info`, else `colima status`) also succeeds; a `ddev` binary with a stopped backend otherwise fails silently deep inside the first `ddev start`. Every required CLI tool is on `PATH`: `uv`, `jq`, and `curl` (the sealed-container unseal is a `uv`-run helper with `pynacl` as an inline dependency, so no separate encryption or checksum binary is required).
   - **Production.** `GET /status` on the configured Kntnt Extractor endpoint for the target production URL, proving it is reachable and reports **Extractor API version ≥ 2** — the version that ships the `environment` endpoint, structure-only extraction, and caller job listing together. An absent, unreachable, or too-old Extractor fails here with a precise install-or-upgrade instruction. The floor is only half the check: the skills are also **verified against Extractor API version ≤ 7**, and a `GET /status` reporting a higher version stops for the operator. The artifact's own shape is bound to the API version — version 5 turned one segment per table into one *or more*, and a client that had not been updated kept only the last slice of every table, losing data with no error anywhere — so an unverified version can silently mis-reassemble rather than fail. Report the reported version and this client's ceiling, and ask whether to continue; under `--yes`, with no operator present to own that risk, abort with the same message and the remediation: update kntnt-wp-skills, or pin production's Extractor to a verified version. If several endpoints could be the target, or the configured base URL does not match the intended production URL, ask which to use rather than guess.
   - **Credential.** This step also **resolves the credential** per *Credentials*, above — the macOS Keychain item `kntnt-extractor-app-password` first, else the `KNTNT_EXTRACTOR_APP_PASSWORD` environment variable — inside a subshell, verifying it resolves to a non-empty value (e.g. a length check) without ever printing it. Absent from both sources, stop with the precise remediation: *create a Keychain item: service `kntnt-extractor-app-password`, account `<wp-user>@<host>` — or set `KNTNT_EXTRACTOR_APP_PASSWORD`.*
2. **Prove the channel is live, correctly targeted, and authorised.** Establish **who** is authenticated before interpreting any refusal — never the other way round. A refusal from a single endpoint cannot distinguish a missing capability from a failed authentication, and a cached refusal mimics both exactly, so reading a capability failure off a pattern of statuses across endpoints is unsound. Every call in this step carries its own cache-buster and has its headers checked for a cache hit, per *Cache-busting* and *Cache interference* above.
   - **Identity first.** `GET /status` again, this time **with** the credential step 1 resolved, in its own subshell. From Extractor API version 4 the response carries `authenticated_as` — the WordPress `user_login` the credentials actually resolved to — and `capabilities`, each of `kntnt_extractor_operate` and `manage_options` mapped to `true`/`false`. Both members present, with `authenticated_as` equal to the user half of the account name (split on the **last** `@`, per *Credentials* above), is the identity proof, and a `false` in `capabilities` then names exactly which grant that named user is missing. Both members **absent** means the credentials resolved to no WordPress user at all: stop with the three-cause diagnosis — unknown username, stripped `Authorization` header, or a cached error response — and its discriminating test, both in [implementation notes](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/implementation-notes.md#troubleshooting-the-control-channel). Never report that as a missing capability; no grant can fix a request that authenticates as nobody.
   - **Fallback for an older Extractor.** An install reporting API version < 4 has no identity report, so run the cheap discriminating test before blaming any capability: repeat the call with the **same** username and a deliberately **wrong** password. `incorrect_password` proves the `Authorization` header reaches PHP and the username exists — a refusal with the real password is then genuinely about capabilities. `rest_not_logged_in` for **both** the correct and the wrong password proves it is not: the username is unknown, the header is being stripped, or the response is cached (re-run with a fresh `_cb` to rule the cache out). Only once the header and the username are proven may `GET /audit-log` — which is `manage_options`-only — be used to narrow the capability: a `403` from `/environment` beside a `200` from `/audit-log` then means `kntnt_extractor_operate` is missing.
   - **Then the channel.** `GET /environment` on the same credential, in one round trip: a `200` is the liveness proof; its `home_url` proves the channel **targets production**, not the local DDEV site (the verify-targets-prod safety rail — it must match the intended production URL, and if it does not, ask rather than guess); and a `200` proves the user holds **both** `kntnt_extractor_operate` and `manage_options`, since `/environment` is gated on both. A `401` (or a `rest_not_logged_in` / `kntnt_extractor_not_authenticated` body) means the request resolved to no user — go back to the identity step, never to a capability remediation. A `403` is a genuine capability refusal for the identity just established; from API version 4 its error code names the missing grant outright (`kntnt_extractor_missing_operate_capability` or `kntnt_extractor_missing_manage_capability`), so remediate that grant, for that named user.
3. **Sweep stranded jobs.** `GET /extractions` lists the caller's own non-terminal jobs, and `DELETE /extractions/{id}` cancels each — leftovers of an aborted earlier run, belt-and-braces with the plugin's own TTL cleanup. Runs before the preflight (step 4) so a batched pair of calls can never cancel the preflight's own probe job; this sweep must never run concurrently with an in-flight preflight. Additionally call `GET /extractions?state=all` — unconditionally, with no version check and no `honours` read first: WordPress silently ignores a query parameter a route has never registered, so against production's 0.4.0 this call is answered exactly as the plain listing above and costs nothing; against an Extractor that has landed the parameter it additionally admits the caller's own **terminal** jobs. Report — never act on — any terminal job the plain listing did not already show: its id, state, and timestamps, for the record; a terminal entry never carries a `download_url`, so this is informational, not proof an artifact is still live on production. Never cancel or consume a terminal job the sweep did not create this run — it may be another operator's, or a deliberately retained diagnostic. Never make the sweep's cancel of non-terminal jobs, or anything else in this step, conditional on this call's success: if it errors, log it and move on exactly as if it had not been made.
4. **Preflight the download path.** Submit a throwaway minimal extraction — `POST /extractions` for **exactly two** tiny structure-only tables and no files, `{table_prefix}options` and `{table_prefix}users` with `table_prefix` taken from step 2's `GET /environment` response (both tables exist in every WordPress install, and a structure-only dump is DDL-only, so table size is irrelevant), sealed to a fresh public key from `echo '{"private_key_path": "<scratchpad>/preflight.key"}' | uv run ../clone/scripts/unseal.py keygen` — poll it to ready with `uv run ../clone/scripts/poll_extraction.py` (the preflight's overall budget is 10 minutes; the Application Password is `KNTNT_EXTRACTOR_APP_PASSWORD` in that one process's environment, never argv), fetch its one-time `download_url` over HTTPS from the local side, unseal it with `../clone/scripts/unseal.py unseal` (stdin `{container_path, private_key_path, sql_path, files_root, tables, structure_only, files}`; full contract in [implementation notes](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/implementation-notes.md#download-and-unseal-local)), then **consume** the job with `POST /extractions/{id}/consume`. This exercises the real serving path — permissions, extension rules, basic auth, WAF/CDN behaviour — before the heavy extraction; the one-time link commonly 404s or is WAF/CDN-blocked on managed hosts. Two tables mean exactly two packaging chunks, so the probe also exercises the continuation path — a one-chunk job completes on the create-time kick alone and never touches it, which is exactly how a dead continuation loopback stays hidden until mid-run ([ADR-0018](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0018-poll-discipline-and-two-chunk-preflight.md)). Verdict by measured wall time from the `201` to the first `ready` poll: **≤ 90 s** passes silently; **slower but ready within the 10-minute budget** passes with a loud warning and an operator gate — *"This host advances extraction jobs at backstop cadence (~N s per chunk, measured by the preflight); the heavy extraction may be impractically slow. Upgrade Kntnt Extractor to ≥ 0.2.1 (Kntnt/kntnt-extractor#18/#19); if it is already ≥ 0.2.1, the host's PHP worker can neither detach from the client nor reach its own loopback URL — fix the host's loopback, or expect the job to advance only one 15 s packaging budget per cron cycle."* — then ask the operator whether to continue or abort; continuing can be legitimate (a small site, or a ≥ 0.2.1 host whose watchdog packages a full budget per cycle), but the operator must own that choice, so under `--yes`, with no operator present to own it, the slow verdict aborts with the warning as the remediation. **Not ready within the 10-minute budget** — the poll discipline's stall rule applies inside it too — aborts the health check with that same message as the precise remediation.

A fast preflight is not a promise about the main extraction. It is measured on two structure-only tables; a pass in a few seconds correctly proves the loopback and continuation path work, but says nothing about how a large table or a large file will behave.

## 2. Discovery

Discovery is reconstructed client-side from three sources, in order, and split across two extraction phases because the classification that shapes the heavy extraction must be computed *before* that extraction exists ([ADR-0017](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0017-discovery-over-extractor-rest-two-phase.md)). The **database password and the other production secrets never enter model context** — the `environment` endpoint masks the secret define family server-side, and the database is never fetched in cleartext.

1. **`GET /environment`** supplies the runtime and configuration scalars: home and site URLs, content and uploads paths, the WordPress core version, the table prefix, the PHP version (to pin DDEV's at major.minor), the database server flavour/version/collation (MySQL 8 vs MariaDB, to pin DDEV and avoid the collation import crash), the active plugins and whether a multilingual plugin is among them, the drop-ins present, and the resolved `wp-config` defines with the secret family already redacted.
2. **`GET /tables` and `GET /files`** supply the sizes and enumerations: the authoritative table list with per-table row-counts and byte sizes, and the whole install-root tree (path + size + mtime) — not scoped to content, and including WordPress core (`wp-admin/`, `wp-includes/`, the root core PHP files); nothing keeps core out of this manifest server-side, so the client-side resolved exclusion set is what keeps it out of the transfer. `GET /files` is **paged via an opaque `cursor`** — loop, following the cursor until it is null, and flatten the pages into one manifest.
3. A cheap **bootstrap extraction** — a normal `POST /extractions` of `wp_posts`, `wp_postmeta`, `wp_users`, the active recognised-mailer tables, and Action Scheduler, and no files, sealed to a fresh public key from `echo '{"private_key_path": "<scratchpad>/bootstrap.key"}' | uv run ../clone/scripts/unseal.py keygen` — is polled to ready via `GET /extractions/{id}`, downloaded to `<scratchpad>/discovery-classify-<stamp>/bootstrap.container` — the role owns a per-run working directory of its own beneath the scratchpad and writes every bootstrap artifact inside it, which is the one layout the close-out's probe globs for — reassembled with `../clone/scripts/unseal.py unseal` into `<scratchpad>/discovery-classify-<stamp>/bootstrap.sql`, parsed with `uv run ../clone/scripts/bootstrap_parse.py` (input `{ sql_path, table_prefix, container_path, private_key_path }`), then **consumed** with `POST /extractions/{id}/consume`. It yields the three signals that need row-level data: the generated-thumbnail exclude-set (from `_wp_attachment_metadata`), the verify-phase entity counts (`wp_users` is carried here so `entity_counts.users` has a source), and the mass-send poised-campaign scan. The bootstrap is small only where `wp_postmeta` is small — a bloated table is a known case of that premise, not a reason to skip `wp_postmeta` ([ADR-0017](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0017-discovery-over-extractor-rest-two-phase.md)) — and is consumed before the main extraction starts, so Extractor's one-active-job rule is never contended. Naming `container_path` and `private_key_path` in the payload makes `bootstrap_parse.py` delete the unsealed `.sql`, the sealed container, and the ephemeral private key itself the moment it has parsed them — the local analogue of `consume` closing the production side, so the cleartext dump (real user and subscriber rows) never outlives the step that consumed it (issue #49).

Assemble the three sources plus the bootstrap parse into one envelope — `{ "api_version": <the health check's GET /status api_version, passed through, never re-fetched>, "environment": <GET /environment>, "tables": <GET /tables>, "files": <flattened GET /files manifest>, "bootstrap": <bootstrap_parse.py output> }` — and pipe it to `uv run ../clone/scripts/discovery.py`; it writes the **canonical discovery document** (redacting any secret define value again at the boundary as a second line of defence). Pipe that document to `uv run ../mkwp/scripts/classify.py` to get the classifications: the full-data / empty table split (with form-submission tables tagged their own `user_submissions` category — [ADR-0014](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0014-user-submissions-own-gate-default-empty.md) — and a recognised CRM/mass-mailer's subscriber tables their own `crm_subscribers` category — [ADR-0019](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0019-crm-subscribers-own-gate-default-empty.md)), the portable vs auto-excluded defines, the flagged heavy blobs, the thumbnail exclude-set, and the derived project and directory names. If either helper exits non-zero, stop and report its stderr diagnostic — a malformed scan never rides into the run.

**Run the `discovery-classify` role here** (`../clone/roles/discovery-classify.md`, by the tier *Role execution* above settles). It makes the `GET /environment`, `GET /tables`, and paged `GET /files` calls, runs the bootstrap extraction (submit, poll, unseal, `bootstrap_parse.py`, consume), pipes the assembled envelope through `../clone/scripts/discovery.py` and `classify.py`, writes the canonical discovery document and the classifications to scratchpad files, and returns only their paths, a one-line summary (table, define, and blob counts; the derived project name), and its evidence block: each helper's exit code, the SHA256 and byte size of both written files, the discovered table and active-plugin counts, `bootstrap_artifacts_deleted` (whether the unsealed dump, sealed container, and private key are confirmed gone), and a `DONE`/`FAILED` marker. Re-read the written discovery document yourself before resolving the plan against it — a `FAILED` marker or a missing evidence block stops the run here, before any gate is presented.

## 3. Resolve the plan and walk the gates

Assemble the resolve envelope — `{ "operation": "resolve", "skill": "pull", "flags": [...], "discovery": <document>, "classifications": <classifications>, "saved_plan": <.kntnt-wp-skills.json or null>, "answers": {} }` — and run `uv run ../clone/scripts/resolve_plan.py`. It returns the run mode, whether this is a replay, the ordered **gate** list, and for every decision its **recommendation**, resolved value, and source layer (built-in < live derivation < saved config < this-run answer, with a flag pinning above all four; `--yes` stops at the saved-config layer). The pull decision list carries the bookend decisions clone does not: the preserved inactive plugin set, the object-cache mode, and deletion mirroring. Both skills' decision lists also carry two sibling privacy gates for tables the classifier tagged privacy-sensitive, both carry/empty, both default **empty**: `user_submissions` for form-entry tables ([ADR-0014](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0014-user-submissions-own-gate-default-empty.md)) and `crm_subscribers` for a recognised CRM/mass-mailer's subscriber store ([ADR-0019](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0019-crm-subscribers-own-gate-default-empty.md)). Each gate's resolved choice is folded independently into `db_table_content`'s own resolved value and recommendation — a carry moves that gate's tagged tables from the decision's empty list into its full-data one, and one gate's carry never disturbs the other's tables — so `db_table_content` is always the one list `../clone/scripts/build_selection.py` builds the extraction's `tables` / `tables_structure_only` split from; this is exactly why the walk re-runs `resolve_plan.py` after every answered gate, so a privacy-gate answer given after `db_table_content` was already walked still folds into the selection that is extracted.

Walk the returned gates in order. For each, present the recommendation and accept on `Y`; on `n`, reveal the alternatives and record the operator's answer, then re-run `../clone/scripts/resolve_plan.py` with that answer in `answers` so the resolved value and every dependent recommendation stay consistent. In `--yes` mode present nothing — every recommendation is accepted — and accumulate the record. When a saved plan exists, present only the single *Replay the saved plan?* gate (plus the mail gate if the valve re-surfaced it).

The mail decision leads with its `findings`: when the mass-send valve flipped, the gate opens with the loud, specific warning naming the engine, the campaign, and the recipient count. Once the walk is done, persist the accepted plan by running `../clone/scripts/resolve_plan.py` with `{ "operation": "save", "resolved": <resolved plan>, "saved_plan": <.kntnt-wp-skills.json or null>, "source": { "extractor_endpoint": <the health-checked Extractor endpoint's base URL>, "live_url": <discovery `home_url`> } }` and writing the result to `.kntnt-wp-skills.json` — the settled decisions and the persisted `source` (the Extractor endpoint and live URL, stored opaquely by `resolve_plan.py`), never the computed lists. Pass the prior saved plan back so the save carries forward any key a pull does not walk — notably the DDEV `target` a preceding clone recorded, and the `source` if this run does not resupply it — rather than dropping it on the re-save.

## 4. Pull bookends — verify the prefix, diff the baseline

The pull-only setup over the local site that already exists. Both steps run before the extraction: the prefix guard fails cheaply, and the diff decides what the extraction even contains.

- **Verify the table prefix.** Read the local table prefix from the marked block in `wp-config.php` and compare it to production's `table_prefix` from discovery. On a **mismatch, abort before any extraction or import** — importing production's tables under a prefix the local install does not read leaves WordPress finding zero tables (platform constraint 12). This is the pull manual page's before-import guarantee; the later marked-block step re-writes this verified-equal prefix into the block (a value no-op, since production's `table_prefix` and the local one match here), so its envelope still carries `table_prefix` — this step's job is to prove the match cheaply before any extraction, not to change what the marked-block step writes.
- **Assemble the resolved exclusion set.** Pipe `{ "classifications": <the classifications `classify.py` produced>, "plan": <the resolved plan `../clone/scripts/resolve_plan.py` returned> }` to `uv run ../clone/scripts/build_exclusions.py` — **never assemble the set by hand**. It unions its canonical `ALWAYS_EXCLUDED` constant (the configuration file and its credential-bearing backup/swap/variant siblings, `.env` files anywhere in the tree, root-level SQL dumps and key material, drop-ins, logs, the known cache-plugin and backup-tool trees, the Extractor's own transfer-staging directories, upgrade dirs, and the whole WordPress core tree — `wp-admin/`, `wp-includes/`, and the root core PHP files — the single source of truth for the always-excluded paths) with the decision-gated thumbnail, blob, and media exclusions and emits `{ "exclusions": [...] }`. This one set is what the diff below filters the manifest against and what the next clone/pull baseline is taken under, so a scope change can never poison the deletion diff (issue #35).
- **Diff the baseline.** Read the stored baseline `.kntnt-wp-skills/last-sync.json` (path → size + mtime, and the scope it was taken under). Fetch production's **whole** install-root tree with **`GET /files`** — paged via the opaque `cursor`, looping until it is null — unfiltered, so the exclusion set never travels to production, a small request whatever its size (issue #18). Filter it locally: pipe `{ "entries": <the flattened `GET /files` manifest's entries>, "unreadable": <any subtree the walk could not read, else an empty list>, "exclusions": <the resolved exclusion set — the `../clone/scripts/build_exclusions.py` output above, never a separately-assembled list> }` to `uv run ../clone/scripts/filter_manifest.py`, which restricts it to the in-scope entries and attaches the resolved set as its scope; it aborts loudly instead if the manifest reports any unreadable directory, since a silently-incomplete tree cannot be trusted for the deletion gate. Combine the stored baseline with that locally-filtered manifest into `{ "baseline": <stored last-sync.json>, "current": <locally-filtered manifest> }` and run `uv run ../clone/scripts/baseline_diff.py`; it returns `new_or_changed` (the set to extract and pull) and `production_deleted` (the set the deletion gate draws from), the deletion set already restricted to paths still in scope this run (the scope-intersection rule, [ADR-0006](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0006-baseline-manifest-diff-with-scope.md)). **Never diff the local filesystem** — local mtimes are unreliable through the archive-and-sync chain, so both sides of the diff are production mtimes (platform constraint 19). Keep the locally-filtered current manifest: it becomes this run's new baseline once localisation succeeds.

Only `new_or_changed` is extracted and transferred, but **the database is always dumped in full** — trimmed by the empty-table classification it is small and not worth diffing.

**Run the `manifest-baseline-diff` role here** (`../clone/roles/manifest-baseline-diff.md`). Fetching production's unfiltered `GET /files` tree, scope-filtering it locally via `../clone/scripts/filter_manifest.py`, and running `../clone/scripts/baseline_diff.py` against the stored baseline are its whole scope: it writes the locally-filtered current manifest and the diff helper's stdout (the `new_or_changed` and `production_deleted` sets) to scratchpad files, and returns their paths, the `new_or_changed` and `production_deleted` counts, and its evidence block: the manifest's row count before and after scope filtering, the helper's exit code, the SHA256 of both written files, and a `DONE`/`FAILED` marker. Read the returned diff-output path for the actual `new_or_changed` and `production_deleted` sets — the extraction step below carries the former, the deletion gate itemises the latter. Confirm the manifest's row count structurally against the evidence block's `manifest_scoped_rows` — e.g. `jq '.entries | length' <manifest path>` — before trusting the diff; the manifest is single-line JSON, so `wc -l` on it proves nothing.

## 5. Extraction on production (background job)

Build the extraction's **selection** from the resolved plan — **never assemble it by hand**. Pipe `{ "table_content": <the resolved plan's `db_table_content` decision, its `full` and `empty` lists — never the classifications' raw table split, which `resolve_plan.py` has already folded with the resolved `user_submissions` gate (ADR-0014)>, "files": <the `new_or_changed` paths read from the diff-output file the `manifest-baseline-diff` role wrote in step 4, not the whole tree> }` to `uv run ../clone/scripts/build_selection.py`; it emits `{ tables, tables_structure_only, files }` — content/CRM tables carried in full, every empty-classified table as structure-only DDL, the new/changed file set — and refuses a self-overlapping or empty selection locally (platform constraint 1). The file set is an explicit list of paths already in scope: `new_or_changed` was diffed against the manifest under the resolved exclusion scope (step 4), so no command-line exclusion patterns or argument-limit hazards arise, and the database is still submitted **in full** (`tables` / `tables_structure_only`), trimmed only by the empty-table classification.

Generate the run's ephemeral key pair with `echo '{"private_key_path": "<scratchpad>/run.key"}' | uv run ../clone/scripts/unseal.py keygen` — it writes the raw private key to a file that never leaves this machine and prints only the base64 `public_key`. Submit the selection with **`POST /extractions`**, carrying that `public_key` and **`strict: false`**, so a file that vanished between the `GET /files` walk and the POST is skipped rather than failing the whole submission; the plugin returns `201 { id, state: "queued", skipped_files? }` and runs the extraction as its own detached background job **outside the docroot**, sealing each table and file segment into the `KNTNTEXT` container. Surface any `skipped_files` the create or a later poll reports — they are gone from production, not a transfer error. A missing *table* is still a hard `404` (the error `data` names every missing table and every missing file). No passphrase is ever generated, fetched, or web-served — the data is sealed to the run's **ephemeral** public key, and only the never-transmitted private key can open it; the database dump, the live-safe read, the sealing, and the outside-docroot staging are all the plugin's responsibility, not the skill's.

A `422` whose `code` is `kntnt_extractor_restricted_path` is the one submission failure that is **not** fatal on the first occurrence: the Extractor refuses to package a path whose name matches a restricted shape — a configuration-file backup, key material, or a database dump at the install root — and names every offender in `data.paths`, so report those paths to the operator with that reason, drop exactly them from the selection's `files`, and resubmit the create **once**; a second such refusal is a hard stop, and the resubmitted selection is what the unseal in §6 reconciles against. The exclusion set above is a pre-filter that makes this rare, never a mirror of the Extractor's policy — that policy lives in the plugin's own repository and may widen between releases without an `api_version` bump ([ADR-0024](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0024-a-restricted-path-refusal-drops-the-named-paths-and-resubmits-once.md)).

**Run the `extract-submit` role here** (`../clone/roles/extract-submit.md`). The submission is all of it — the `POST /extractions` above, the one corrected resubmission if the server refuses a restricted path, and writing the accepted job to `<scratchpad>/extract-job.json` before it returns: the job id, the selection exactly as submitted, and any `skipped_files`. It never waits for the job, because the wait below is yours. It returns a short summary and its evidence block: the job id and its `queued` state, the job record's path and SHA256, the submitted table and file counts, any skipped or refused paths, and a `DONE`/`FAILED` marker carrying the failing status and body on `FAILED`. Re-read the written job record yourself and check its `job_id` and SHA256 against that evidence block before the poll starts — one `sha256sum` against the id you are about to wait hours on.

**The main extraction's poll is the orchestrator's own work.** You run it yourself, in the context reading this: it is never delegated to a subagent and never detached from this session. Start it as your own tracked background job and let the harness tell you when that job has finished — while it runs, do not query the extraction yourself, do not spend a sleep loop watching it, and never `nohup` it or otherwise put it beyond the bookkeeping that would notice it die. In a harness with no background jobs at all, run the identical command in the foreground and block on it; what may never happen is that the process waiting on this job belongs to something that can be reaped out from under it. This wait used to belong to a subagent, and on both production runs of this engine that subagent returned without a verdict — the second time having detached the poll first, so it died with the agent's process tree while the job ran on to 13,459 files with nobody watching. Since the written close-out for a verdict-less return is `DELETE`, only an unwritten manual state check stood between a healthy extraction and a cancel ([ADR-0027](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0027-the-orchestrator-owns-the-main-extractions-poll.md)). Asking an agent more firmly not to escape a multi-hour wait had already failed twice; this is the boundary moved instead of reworded.

Run exactly: `KNTNT_EXTRACTOR_APP_PASSWORD="<resolved inside this same subshell>" uv run ../clone/scripts/poll_extraction.py "<extractor_endpoint>" "<job_id>" --user "<user>" --log "<scratchpad>/extract-poll.log" > "<scratchpad>/extract-poll.json"; echo $? > "<scratchpad>/extract-poll.exit"` — the job id read back from `<scratchpad>/extract-job.json`, the secret resolved in the prefix form inside that same subshell and never on argv. The three files are what make the poll's result survive the poll. `extract-poll.log` fills up as the job advances, so it is the only one of them worth reading while the wait is on. `extract-poll.json` holds the one JSON verdict, printed at the very end — which means it is zero bytes for the whole run and proves nothing on its own. `extract-poll.exit` is written the instant the helper exits and is therefore the discriminator: an `extract-poll.json` with no `extract-poll.exit` beside it means the poll died rather than answered, and says nothing whatever about the job. Recovering from that is not a decision, it is a repeat: the id is already on disk, polling is read-only, so re-attaching to a job whose id you have costs nothing — run the identical command again. Reach for the close-out below only once a verdict, or the job's own state, actually says the extraction is finished with.

**The discipline the helper implements**, unchanged by who invokes it: it polls `GET /extractions/{id}` every 15 s after a successful poll, with a 120 s per-request timeout, until `state == "ready"` and `download_url` is non-null; the main extraction has no overall wall-clock budget — the stall window is the stop. On a transport timeout, connection error, or 5xx: log it and retry after 30 s (60 s from the second consecutive failure), resetting to the 15 s cadence on the next success — a single bad response is never failure. The `progress` counters are reported between polls (e.g. `tables 5/12, files 40/312`), so a slow-but-advancing job is visibly distinct from a wedged one; the job counts as advancing when its `state` changed, when `progress.chunks_done` increased, or when the sum `progress.tables_done + progress.files_done` increased, and structure-only tables count toward that progress. **`chunks_done` is the one that matters** (Extractor API version 6 and up): the other counters move only when a whole table or a whole file finishes, so a job working steadily through one large table looks identical to a wedged one — observed as `3/186` standing still for minutes on a healthy run, and worked around by widening the stall window to 2400 s, which is how a real stall comes to take forty minutes to notice. Against an Extractor below version 6 the field is absent; fall back to the two coarse counters and widen to the 40-minute stall window instead of the 10-minute one, and say in the run's output that you did. Failure is exactly: `state == "failed"` (surfacing the `error` the plugin reports), a confirmed-vanished job (a `404`, treated as a transport-class fault and retried under the existing 30 s / 60 s backoff, that also `404`s on re-poll with the id absent from `GET /extractions` — a single `404` is logged and retried, never terminal on its own, and polling continues within budget), no advance within the 10-minute stall window — aborting rather than hanging, and never on transport errors alone ([ADR-0018](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0018-poll-discipline-and-two-chunk-preflight.md)). The canonical statement of this discipline — and the source the consistency tests read their pinned phrases from — is [docs/poll-discipline.md](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/poll-discipline.md); it is restated here in full because a surface loaded on its own must carry the whole rule set.

## 6. Download, verify, and unseal

Fetch the one-time `download_url` over HTTPS with `curl -fSL -C - --retry 3` (resume and retry) into `<scratchpad>/extract.container.part`, rename it to `<scratchpad>/extract.container` once the transfer command exits cleanly, then open it with `uv run ../clone/scripts/unseal.py unseal` — stdin `{container_path, private_key_path, sql_path, files_root, tables, structure_only, files}`; full contract in [implementation notes](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/implementation-notes.md#download-and-unseal-local) — and the run's private key: each segment's sealed key is opened (`crypto_box_seal`), each segment decrypted (`crypto_secretbox`), and the container reassembled — the table segments concatenated into one importable `.sql` with a prepended connection-safe preamble (charset `SET NAMES`, `FOREIGN_KEY_CHECKS`, SQL mode), the file segments written to disk by their install-root-relative path. Both outputs have fixed homes — `sql_path` is `<scratchpad>/extract.sql` and `files_root` is `<scratchpad>/extract-files/` — because the close-out's local probe has to be able to ask what this run produced without being told. The `crypto_secretbox` **authentication is what catches a truncated or corrupted download** — a tampered or short segment fails to open, so a bad transfer is caught before it touches the local site; **no separate checksum step is needed**.

**What landed is counted, not what was written.** Production is Linux, where a filename's bytes are stored verbatim, so `å` written as one code point and `å` written as `a` plus a combining ring are two different files; the copy lands on macOS, where APFS normalises, so both spellings name one file and the second write silently replaces the first. The unseal's report therefore carries `files_landed` — the distinct files counted on disk once every write is done — beside `files_written`, and `normalisation_collisions`, one group per set of paths the destination could not keep apart, naming every spelling in the group. A collision is **not** a transfer error and never aborts the run: the container is correct and the destination cannot represent it. It rides the `extract-transfer` evidence block and is named in the run report (§11). See [ADR-0025](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0025-a-destination-filesystem-collision-is-reported-never-fatal.md).

## 7. Close the exposure window

Immediately after the container unseals, **consume** the job with `POST /extractions/{id}/consume` and confirm it is gone — the happy-path close that deletes the artifact on production. The plugin's own TTL/watchdog cleanup and the next health check's stranded-job sweep are the backstops; this explicit consume keeps the exposure window to minutes even so. `DELETE /extractions/{id}` is **only** for cancelling a stranded or aborted job (the health-check sweep), never the happy-path close. A consume refused **`409 kntnt_extractor_locked`** is a tick or the TTL sweep holding the job's per-job lock, not a failure: it is retried up to five times, 10 seconds apart — six attempts across roughly 50 s, more than three of the Extractor's 15 s default `tick_budget`, which is the longest hold its own lock discipline permits. A refusal that persists through that whole window leaves the sealed artifact on production until its TTL, where the next run's health-check sweep clears it, and the transfer itself is complete: the download and the unseal both precede the consume, so the local copy is sound.

**Run the `extract-transfer` role here** (`../clone/roles/extract-transfer.md`). Steps 6–7 — reading the job record, confirming in one `GET /extractions/{id}` that the job is still `ready`, downloading, unsealing, and consuming — are its whole scope: it writes the reassembled dump and the unsealed files to scratchpad paths and returns only those paths, the observed job state, and its evidence block: the job id and `state`, the reassembled-dump and unsealed-files byte sizes, the SHA256 of the reassembled `.sql`, and confirmation that the job was consumed. It never submits a job and never waits for one — a job that is not `ready` when it looks comes back as a `FAILED` verdict for you to settle, never as a second poll. Re-run `../clone/scripts/dump_sanity.py`'s verdict on the reassembled `.sql` yourself before treating the extraction as trustworthy — an evidence block claiming `DONE` against a failed dump-sanity verdict is treated as `FAILED` regardless.

### Closing out a failed phase

Any `FAILED` return from `discovery-classify`, `extract-submit` or `extract-transfer` — including a return the engine reads as `FAILED` because it arrived without its evidence block — any terminal verdict the main extraction's poll returns other than `ready`, and any abort the orchestrator itself takes after a job has been submitted, is followed by a close-out before the run stops — a run may never end with a job this orchestrator submitted left unaccounted for. The role files shape their `FAILED` verdict specifically so this close-out has what it needs (the job id, the last observed state, and — from `extract-transfer` — the phase the failure occurred in and the downloaded container's local path when a download completed); this is where that handoff is discharged. What it supplies above all is the **job id** — the case itself is derived below, from the job and from this machine, never read off the phase a role happened to report.

**Re-query the job before choosing a case.** On any `FAILED` verdict — and equally on an **absent or malformed verdict**, a result that arrived without the evidence block that would make it one — issue a single `GET /extractions/{id}` before selecting a close-out case at all. The job's own reported state outranks the subagent's claim about it: if the job reports `running` with progress that has advanced since the last observation, the result is unreliable and the **job is not** — select no close-out case, resume polling the same job id, and let the run continue. An absent verdict is **not** evidence of an exhausted stall window; silence carries no information about the job at all, and reading the least informative return as the most specific case is exactly what routes a healthy extraction onto the cancelling branch. That is not hypothetical: it stood between a live extraction and a `DELETE` on two production runs, one of them two and a half hours in and visibly advancing — `state: running`, `chunks_done` climbing — with only an unwritten manual check of the job stopping the cancel ([ADR-0022](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0022-close-the-exposure-window-on-every-failure-path.md)). The re-query is one call and it gates the cancelling branch only: it never postpones case 2's `consume`, which is reached on a download that already succeeded and stays exactly as it is.

**Derive the case; never read it off a reported phase.** Two authorities settle which case applies, and no claim from a session is one of them: first the job's own state, from the single `GET /extractions/{id}` above, and then **this machine's own state** — what the run's scratchpad actually holds. Only `extract-transfer` reports a `failure_phase` at all; `discovery-classify` and `extract-submit` have no such field in their evidence blocks, and an absent verdict carries none by definition, which is what makes it absent. A case list switched on that field therefore leaves three routes into this close-out undefined, on a job that may hold hours of extraction. Where a phase *was* reported it is a **hint, never the selector** — corroboration for the report and for the run record, and the vocabulary stays exactly as it is — and where the hint and the derived state disagree, **the derived state wins**. This is the precedence the spec already states (a remote authority outranks a local claim about remote state) carried one step further, to the machine's own state over a session's claim about it.

**Where the probe looks, and what a name means.** A run's sealed container reaches its final name only once it is whole: the download writes `<scratchpad>/extract.container.part` and, only after the transfer command exits cleanly, it is renamed to `<scratchpad>/extract.container`. The final name existing *is* the answer to *was a sealed container downloaded?*, and a lone `.part` is an interrupted or failed download — never a container to consume against, since consuming on the strength of a truncated file would destroy the only whole copy. The reassembled dump is `<scratchpad>/extract.sql` and the unsealed files tree `<scratchpad>/extract-files/`; a non-empty dump is the answer to *was it unsealed?*. `discovery-classify`'s bootstrap job answers the same two questions inside that role's own per-run working directory — `<scratchpad>/discovery-classify-*/bootstrap.container` (with the same `.part` rule) and `bootstrap.sql` beside it — globbed, because the directory name carries a timestamp and a random suffix and a second attempt leaves a second directory: read the newest match, and where more than one exists say so in the report rather than choosing silently. The probe only reads: it creates, moves and deletes nothing, and being local it costs no call and postpones nothing — least of all case 2's consume.

**Every combination has an outcome; none is left to inference.** The job's state and the probe together select exactly one of the four cases below, or explicitly select none:

| What the two authorities say | What the close-out does |
|---|---|
| `queued` or `running`, and the job is advancing — its `state` changed or its `progress` counters rose since the last observation | **No case — resume polling.** The verdict was unreliable and the job is not; resume the same job id and let the run continue. |
| `queued` or `running`, and the job is not advancing — the poll's own terminal verdict, or an abort the orchestrator itself took, after which no poll will ever resume | **Case 1** — cancel. |
| `failed`, or a **confirmed-vanished job** (a `404` re-confirmed by a re-poll and a `GET /extractions` listing check) | **Case 1** — cancel. |
| `ready`, and the probe finds no container at its final name — nothing, or only a `.part` | **Case 3** — report, do not act. |
| `ready`, and the probe finds the container at its final name | **Attempt the consume.** It answers `consumed` and the run closed as **case 2**; refused `409 kntnt_extractor_locked` through the whole bounded retry window, and that refusal is **case 4**. |
| `consumed` | **No case — the job is already accounted for.** The artifact is already gone from production and there is nothing left to close; report the original failure and stop. |
| The one `GET` **could not be answered** — a transport fault, or an authentication or cache refusal | **No case — the job's state is unknown.** Report the job id, the endpoint, and that its state could not be established; §1.3's sweep and the plugin's TTL are what reclaim it. Absence of information never selects the destructive case — that is the whole of the rule above. |

Whether the container was also *unsealed* changes no row's action, only what the report says: a `ready` job whose container is on disk is consumed either way, because the download precedes the unseal and the local copy is already as complete as it is going to get. That is also why cases 2 and 4 share a row. They present identically on disk — both are a `ready` job, downloaded and unsealed — and the field that once told them apart is the field this derivation demotes, so the difference is not detected but observed: case 4 is the name for what happens when case 2's action is refused. The risk is asymmetric and makes that an easy trade rather than a balanced one — a consume that turns out to be unnecessary costs the bounded retry window and nothing else, while one that was needed and never attempted leaves the sealed artifact on a live client site until its TTL.

The four cases that table selects among:

1. **The job never reached `ready`** — a `failed` state, a confirmed-vanished job, or an exhausted stall window. `DELETE /extractions/{id}` to cancel it. There is no artifact to preserve, and the job otherwise holds the one-active-job rule against the next attempt.
2. **The job reached `ready` and the container downloaded, but the unseal failed** — `POST /extractions/{id}/consume`. The download precedes the unseal (§6), so a complete local copy already exists; consuming destroys nothing that is not already on this machine, and it closes the exposure window on a live client site immediately rather than at TTL. Report the local container's path so the failure stays diagnosable.
3. **The job reached `ready` but the download failed or never ran** — do **not** act unilaterally. The production artifact may be the only copy of what could be hours of extraction. Report the job id, its state, that the artifact is still published, and that the plugin's TTL will reclaim it; then offer consuming it as its own accept-or-override gate. Under `--yes`, with no operator present to own that choice, do not consume — print the same information for the record instead. Losing a completed extraction to a reflex is a worse outcome than a bounded, reported, TTL-terminated exposure window.
4. **The job reached `ready`, downloaded and unsealed, but every consume was refused `409 kntnt_extractor_locked`** (`failure_phase: unsealed_consume_locked`, where a role reported one, corroborates it) — there is nothing further to attempt. The bounded retry window has been spent, by the role or by the close-out's own attempt, and an unbounded one against a live client site is exactly what that bound exists to prevent. Report that the transfer is complete and the local copy sound, that the sealed artifact is still published on production, and that its TTL and the next run's stranded-job sweep will reclaim it — this is the one close-out case that is not a failed transfer, only a forfeited close.

The close-out is best-effort and never masks the original failure: a close-out call that itself fails is reported alongside the original cause, and the run still stops on the original cause — a cleanup error must never become the headline.

§1.3's stranded-job sweep is the backstop, not a substitute for this: it only runs on the *next* run, and it lists only the caller's own non-terminal jobs, so a job that has since failed server-side is invisible to it by the time that next run starts. This close-out is what keeps the exposure window to the current run instead of the next one.

Keep §7's distinction intact here too: `DELETE` is for cancelling, never the happy-path close — case 1 above is a cancel, case 2 is a consume.

When the failing phase was `discovery-classify` and it left the cleartext bootstrap dump in place (`bootstrap_artifacts_deleted: false`), report its exact path and state plainly what it holds — a **cleartext** dump including real user rows and, when a recognised CRM was carried, real subscriber rows — then delete it before the run ends, unless the operator explicitly chooses to keep it for diagnosis: an accept-or-override gate defaulting to **delete**. Under `--yes`, delete it without asking and say so in the record — an unattended run has no operator to read a diagnostic, and leaving production personal data on disk unattended is the worse default.

## 9. Import and localise

Local and destructive. Run in this exact order — the order is a safety rail ([spec](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/spec.md) *Import and localise*):

1. **Rollback backup (pull only, before anything destructive).** Back up the local database with `ddev export-db` to the durable, gitignored `.kntnt-wp-skills/backups/local-pre-import-<timestamp>.sql.gz` **before any destructive local step** — a bad refresh is then one import away from undone. Keep its path for the report (review point 18 in `docs/implementation-notes.md`).
2. **Sanity-check the dump.** Run `uv run ../clone/scripts/dump_sanity.py` with the discovered prefix and the resolved plan's `db_table_content` empty-table list (the same folded list step 5's selection carried, not the classifications' raw split) against the reassembled dump: the content table created under the prefix, its inserts present, every one of those tables created but empty. Abort on any failure — a wrong-prefix dump leaves WordPress finding nothing.
3. **Import.** `ddev import-db` the reassembled dump; verify table and post counts afterwards.
4. **Merge the unsealed files.** `../clone/scripts/unseal.py` wrote the extraction's file segments to a staging tree by their install-root-relative path; merge that tree over the content directory as a **merge**: the local `wp-config.php` and local-only files survive; production's plugin, theme, and media files in the new/changed set overwrite.
5. **Deletions, if enabled (off by default).** Deletion mirroring is **off by default** ([ADR-0010](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0010-deletion-mirroring-opt-in-trash.md)); when the remembered per-site answer is Yes, itemise the two sources — the `production_deleted` set read from the diff-output file the `manifest-baseline-diff` role wrote (step 4) and the plugin/theme **drift** (local plugins/themes with no production counterpart, as a checklist) — and move confirmed items to the timestamped local trash `.kntnt-wp-skills/trash/<timestamp>/`, **never a hard `rm`**, reversible until emptied, and report the path. Under `--yes` nothing is ever removed **without a saved Yes** already on record — a `--yes` run never turns a No, or an unanswered default, into a deletion.
6. **Object-cache drop-in (pull only).** Resolve the drop-in by the **ownership rule** — no local drop-in → nothing; a different owner than production → keep local; the same owner → take production's — then **verify a real request succeeds** and **auto-remove** the object-cache drop-in on failure, reporting it. A production drop-in pointing at a loopback cache host is fatal against DDEV (platform constraint 16).
7. **Write the marked block.** Read the current `wp-config.php`, then pipe `{ "wp_config": <its full text>, "defines": <`classifications.defines.portable` verbatim — the classifier's `[{ "name", "value" }]` records, the value source>, "select": <the resolved `wp_config_defines` decision's value — the *names only* the gate kept>, "table_prefix": <the prefix already verified in step 4 — passing the verified-equal value is a no-op in value>, "cron": "run" (or "disabled" if `--no-cron`, folding step 8's cron decision in here) }` to `uv run ../clone/scripts/wpconfig_block.py` and write its returned `wp_config` back. **Never hand-join the names to values yourself** — pass the two artifacts as they stand and let the helper join them deterministically, writing only the selected names each valued from its record, so a define deselected at the `wp_config_defines` gate is never ported (issue #42). The helper writes the block and computes the collision removal dynamically, exactly as at clone. Then lint the result: `ddev exec php -l wp-config.php` — **abort on any parse error**. **Surface** in the report any **new production define** of the portable class the classifier found — configuration drift brought to attention rather than silently ignored.
8. **Apply mail.** For the resolved mail mode, either keep the existing mailer or install the capture mu-plugin `../clone/templates/kntnt-wp-skills-mailpit.php` into `wp-content/mu-plugins` (it short-circuits `wp_mail` at top priority to DDEV's Mailpit, catching API mailers that never touch sendmail). The cron decision was already applied by the previous step's `cron` input: `--no-cron` wrote `define('DISABLE_WP_CRON', true);` into the block; otherwise cron is left running.
9. **Re-apply the preserved inactive set (pull only).** Re-apply the **preserved inactive** plugin set — derived from live local state this run — with `ddev wp plugin deactivate <list> --skip-plugins --skip-themes`, so plugin and theme code is **skipped during deactivation** and an object-cache plugin cannot re-drop its drop-in mid-step. Tools you keep off stay off.
10. **URL-scoped search-replace.** One pass per source URL form, each `ddev wp search-replace '<old>' '<new>' --all-tables --skip-columns=guid --report-changed-only --skip-plugins --skip-themes`. The forms, in order: `https://www.<domain>`, `http://www.<domain>`, `https://<domain>`, `http://<domain>`, the protocol-relative `//www.<domain>` and `//<domain>`, the **escaped-slash** forms `https:\/\/www.<domain>`, `https:\/\/<domain>`, `http:\/\/www.<domain>`, `http:\/\/<domain>` that page builders store inside JSON, the **escaped-slash protocol-relative** forms `\/\/www.<domain>` and `\/\/<domain>` (a stored protocol-relative URL has no scheme to anchor the scheme-ful escaped passes), the **double-escaped-slash** forms `https:\\/\\/www.<domain>`, `https:\\/\\/<domain>`, `http:\\/\\/www.<domain>`, `http:\\/\\/<domain>` that JSON-within-JSON storage (a plugin's serialised config nested inside another plugin's JSON option) produces — `\\/\\/` is not a substring of `\/\/`, so the single-escaped pass alone leaves it untouched — and, by the same argument, the **double-escaped-slash protocol-relative** forms `\\/\\/www.<domain>` and `\\/\\/<domain>`. **Never the bare domain** — it corrupts `user@domain` email addresses. Serialised objects wp-cli safely skips keep the old domain; harmless.
11. **Set the URLs.** Set the `home` and `siteurl` options explicitly to the DDEV URL.
12. **Regenerate thumbnails (metadata-driven delta, regenerable names only).** `ddev wp media regenerate` scoped to the affected attachment IDs — the **metadata-driven delta** at pull: compare each attachment's registered sizes against the files on disk, but an attachment only joins the regeneration set when a **regenerable-named** size is missing — a name `wp media regenerate` would itself derive from the attachment's *current* attached file, `<stem>-<W>x<H><ext>` (the same rule `classify.py::thumbnail_exclude_set` applies to the transfer exclusion). **Big-image attachments (#30):** when the attached file's stem ends in the exact, case-sensitive terminal token `-scaled` — WordPress's big-image-size-threshold feature scales an over-sized upload down to `<stem>-scaled<ext>`, but generates every registered sub-size from the *pre-scaled* original — a size regenerable from the stem with that token stripped also counts as regenerable-named, additive to the unstripped-stem match, so these attachments' genuine gaps join the regeneration set exactly as any other attachment's would. An attachment whose only gaps are **non-regenerable** names (production filename drift from a historical WebP conversion, a dedup-suffixed PDF preview, or any other name regeneration can't reproduce) must **never** be fed to `wp media regenerate` — default regenerate deletes-then-rebuilds, so it would delete the transferred drifted file and rebuild it under the wrong (new) name, reintroducing the very 404s the wider transfer scope (#26) was fixed to avoid. This is why change #26 also narrowed the transfer exclusion: after it, a regenerable-named gap should be rare (the file was excluded and needs rebuilding), while a non-regenerable-named gap means the file simply wasn't excluded and already travelled — nothing to regenerate. `--regenerate-all` remains the escape hatch that forces the lot, unfiltered. **Run the `thumbnail-smoke-test` role here** (`../clone/roles/thumbnail-smoke-test.md`), which runs the delta regeneration through `../clone/scripts/wp_quiet.py regenerate`, keeps its per-image progress and warning spam in that step's log file, and returns only the regenerated-attachment count, any genuine anomaly, and its evidence block (the command's exit code, the regenerated count, `DONE`/`FAILED`). A non-zero exit from the regeneration is an **anomaly**, never a `FAILED`: this step rebuilds local derivatives that were deliberately never transferred, so nothing it reports can be evidence that the copy is wrong — the role names it in its `anomalies` list and the run continues ([ADR-0028](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0028-a-phase-fails-on-a-defective-copy-never-on-a-non-zero-exit.md)).
13. **Rebuild the search index.** When discovery's active-plugin list contains a search-index plugin — the `relevanssi` / `searchwp` families `classify.py`'s `OPERATIONAL_TABLE_PATTERNS["search_index"]` also tags — probe `ddev wp cli has-command "relevanssi index"` (resp. `ddev wp cli has-command "searchwp index"`); on success run `ddev wp relevanssi index` (resp. `ddev wp searchwp index --rebuild`). A probe failure (free Relevanssi ships no WP-CLI command at all — WP-CLI support is Premium-only, from 1.15.1) is a **report-only fallback**: leave the index empty and surface one clear line in the run report — search index not rebuilt, rebuild manually from wp-admin (Settings → Relevanssi → Build the index). No active search-index plugin → a clean no-op: no probe, no report noise beyond one line. Like thumbnail regeneration, this is local-only, deterministic, and mutates only local index tables, so it runs automatically with no operator gate. **Run the `thumbnail-smoke-test` role here** (`../clone/roles/thumbnail-smoke-test.md`), folded into the same invocation as the preceding thumbnail-regeneration call; it returns the reindex command's exit code and its outcome (`rebuilt` / `cli-unavailable` / `not-present`) inside its evidence block ([ADR-0015](https://github.com/Kntnt/kntnt-wp-skills/blob/main/docs/adr/0015-search-index-excluded-and-rebuilt-locally.md)).
14. **Flush with plugins loaded.** `ddev wp rewrite flush --hard` — **without** `--skip-plugins`, so the flush runs with **plugins loaded**. A flush that skips plugins silently drops multilingual and custom routes, 404ing every localised subpage.
15. **Restart.** `ddev restart` to clear the PHP-process caches a `wp cache flush` cannot reach.
16. **Write the new baseline.** Store the locally-filtered current manifest kept in step 4 — path, size, mtime per file, and the **scope** it was taken under — as `.kntnt-wp-skills/last-sync.json` (the `../clone/scripts/filter_manifest.py` output over the paged `GET /files` walk), the baseline the next `pull` diffs against.

## 11. Cleanup and report

Remove the large local scratch artifacts (the reassembled dump and the unsealed files), plus any bootstrap-extraction artifacts the discovery phase left behind — `discovery-classify` deletes the unsealed bootstrap `.sql`, its sealed container, and the ephemeral private key itself once `bootstrap_parse.py` consumes them (issue #49), so this is a belt-and-braces sweep, not the primary mechanism. Production is already state-neutral — the extraction job was consumed in step 7 and nothing was left running. This step is reached only by a run that completes — a failed or aborted run stops before ever reaching §11, so the *Closing out a failed phase* subsection under §7, not this sweep, is what covers the failure path.

Report the Extractor API version production's health check reported (`discovery.api_version`), and — when it is below this client's ceiling — name each behaviour that is consequently degraded on this host, one bullet each. At the time of writing there are three: this list is the client's own knowledge of what it assumes about the Extractor, and the remedy for all of it is upgrading production's Extractor, never a client-side workaround.

- **Below API version 4** — `GET /status` carries no `authenticated_as` or `capabilities`, so identity was proven by the deliberate wrong-password discriminating test rather than read directly.
- **Below API version 6** — `progress.chunks_done` is absent, so stall detection ran on the coarse counters and under the widened stall window (§5); a genuine hang therefore took longer to notice.
- **Below the version that added `strict`** — the `strict: false` member is additive and is silently ignored by any Extractor that predates it, so a file that vanished between the `GET /files` walk and the `POST` would have failed the whole submission rather than being skipped and reported; no version number distinguishes an Extractor that honours `strict` from one that ignores it, so this degradation is reported unconditionally against any Extractor whose release predates the one that shipped it. This one is a *deliberate* degradation to the previous behaviour, recorded in `CHANGELOG.md`; the report says so plainly rather than framing it as a fault.

Name the files the copy does not contain: every path in `skipped_files` (gone from production between the manifest walk and the submission) and every path in `restricted_paths` (refused by the Extractor as a restricted shape and dropped from the resubmitted selection, §5). Both lists are ordinarily empty; when one is not, the operator learns it here rather than discovering the absence months later.

Name every group of paths the local filesystem merged: each group in the unseal's `normalisation_collisions`, spelled out path by path as the helper printed them — its JSON escapes the non-ASCII code points, and the two spellings render identically otherwise — together with `files_landed` against `files_written`, so the operator sees how many files the copy actually holds. Say plainly what happened: production keeps the two spellings apart, macOS stores them as one file, and the bytes that survived are whichever was written last, so one variant of each pair is not in the copy. A merged thumbnail or `.webp` derivative is ordinarily harmless because the thumbnail regeneration in §9 rebuilds it; a merged **original** under `uploads/` is not, and nothing in the run can tell the two apart, so the operator is the one who decides what to do about it. This list is ordinarily empty, and a run that reports one is still a complete transfer rather than a failed one.

Report the full decided-and-done record.
