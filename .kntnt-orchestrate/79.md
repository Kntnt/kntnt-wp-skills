# Orchestration notes for #79

## CHANGELOG.md

Under `## [Unreleased]` → `### Changed`:

- **The Extractor API-version pin is now `≥ 7 and ≤ 7`, and every behaviour-level back-compat path has moved off the version number onto the `honours` list.** The floor had not moved since it was set at `2`, while the ceiling had been raised to `7` on evidence ([ADR-0021](docs/adr/0021-verified-against-extractor-api-version-7.md)) and production runs `Status_Controller::API_VERSION = 7` (Kntnt Extractor 0.7.0). Everything between the two was a compatibility claim carried on inspection alone — a number that reads as verification with no verification behind it — and it authorised prose describing hosts no installation runs. Raising the floor to meet the ceiling makes the claim honest: `api_version` bounds the sealed container's byte layout and nothing else, so it moves exactly when this client must stop and be re-verified, and *"verified against the artifact contract as of `api_version` 7, and nothing else"* is the honest statement of what is known. Before the literal moved, every endpoint, request member, response member, and error code this client depends on was confirmed present at `api_version` 7 by reading the Extractor's own source at `v0.7.0` — a green suite is not that verification, since the suite reads this repository's surfaces rather than the plugin. **The raise deletes only what the version number genuinely discriminates.** `authenticated_as` and `capabilities` landed at API version 4 and are not `honours` names, so at the floor every install reports identity: the *below API version 4* degraded-behaviour bullet, the wrong-password step that stood in as a **fallback** for an Extractor too old to report identity, and the `GET /audit-log` comparison that used to disambiguate a `403` are gone — the wrong-password test itself survives in `docs/implementation-notes.md`'s troubleshooting table, answering the question it is actually good for, *why* a request authenticated as nobody. **Everything behaviour-level stays, re-anchored.** The Extractor ships caller-visible behaviour additively, without moving `api_version` ([Extractor ADR-0017](https://github.com/Kntnt/kntnt-extractor/blob/main/docs/adr/0017-api-version-bounds-the-artifact-contract.md)), so a build reporting `7` may honour none of it: the `chunks_done` and `strict` bullets now fire on `honours` — the `strict` one had been firing *unconditionally*, on the stated grounds that no version number distinguishes a host that honours the member from one that ignores it, which was true of the version number and precisely the question `honours` was added to answer — and the degraded-behaviour section is four bullets, every one of them keyed on the list. The widened stall window still fires on `chunks_done` being *observed* absent, and the define-disclosure by-value fallback still fires on the `disclosure` member being absent; neither behaviour changed. **The specification credited the floor for that second fallback**, and [ADR-0023](docs/adr/0023-a-defines-disclosure-is-read-from-the-protocol-member.md) said raising the floor above `6` would make it dead code to delete — a wrong attribution that would have deleted a live defence, since `disclosure` is an `honours` name and the guard is member presence. Both surfaces now name the guard instead of the floor. `scripts/unseal.py` is untouched, including its tolerance of a one-segment-per-table container, which is now defence in depth rather than a supported configuration. See [ADR-0037](docs/adr/0037-the-api-version-floor-rises-to-meet-the-ceiling.md) ([#79](https://github.com/Kntnt/kntnt-wp-skills/issues/79)).
