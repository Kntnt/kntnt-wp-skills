# The poll helper merges the packaging-time skips into the job record

`strict: false` used to mean one thing: a file that vanished between the `GET /files` walk and the `POST` is skipped rather than failing the whole submission. The Extractor widened it (Kntnt/kntnt-extractor#31, Extractor ADR-0026) to cover a file that vanishes **during packaging** — hours into the run, long after the `201` was answered. `skipped_files` therefore stopped being settled at create: the `201`'s list is a lower bound, and the terminal poll's list is the whole of it.

This client froze the lower bound. `extract-submit` writes the `201`'s list into `<scratchpad>/extract-job.json` before the poll starts and nothing revises it; the poll observes the current list, puts it in `extract-poll.json`, and nobody reads it back; `extract-transfer` then tells the unseal to expect the submitted selection minus that frozen list. `unseal.py`'s `_validate_selection` compares the container's distinct file names to the expected list with **strict equality**, so a file skipped mid-run is not an under-count — it is a refusal, and the run returns `FAILED` after the download and after the whole extraction. On the production run that motivated the plugin-side change, that is six hours spent and lost at the final step.

The current list is already on this machine. What was missing is the step that carries it to the unseal. The question is only which surface owns that step.

## Decision

**The poll helper owns the merge.** `skills/clone/scripts/poll_extraction.py` takes an optional `--job-record <path>`, and on reaching a terminal verdict — `ready`, which is the one an unseal follows, or `failed`, which makes the report honest — it folds the skip list it observed into that record. `extract-transfer` goes on taking its lists from the job record alone; what it subtracts is now both of them.

Four properties make that merge safe to run at the last step of a six-hour run, and each is pinned by a test in `tests/test_vanished_file_submission.py`:

- **Optional and absent by default.** The preflight and the bootstrap poll throwaway jobs that have no record. No `--job-record` means no merge attempted and behaviour identical to before.
- **A union that never shrinks.** The plugin appends rather than rewrites, but the client does not depend on that: a path in the record and absent from the poll's list stays in the record.
- **Idempotent.** A lost poller is a re-poll — the skills instruct the operator to re-run the identical command against the same job — so merging twice produces the record merging once produced, with no duplicated entries.
- **Terminal-only.** A transport failure, an exhausted budget, a stall, a cache hit, a confirmed-vanished job: none of them observed anything about packaging, and none of them writes.

**Two lists, not one.** The record keeps `skipped_files` under its existing name and meaning, so a record written before this change stays readable, and gains the sibling `packaging_skipped_files` holding the paths first reported after create. Deriving the packaging-time set as *observed minus recorded* falls out of the same union. They are unioned only where the unseal needs a single list; the run report names them separately, because they say different things — the first that a file was deleted while the client was looking at it, the second that production mutated hours into the extraction. The second is the only place an operator could learn that at all.

**A degraded-behaviour bullet, not a version gate.** The run report already names degraded behaviours one bullet each, with one firing on the `honours` list rather than on the version number. A host that does not name `packaging_skips` cannot produce a mid-run skip, the merge is a no-op there, and that is stated in the same place the others are.

## Rejected alternatives

- **The orchestrator merges.** The natural reading of "the current list is already in `extract-poll.json`": have `SKILL.md` tell the orchestrating agent to read the verdict and rewrite the record. Rejected because it is prose an agent must execute correctly at a six-hour run's last step, on the one path where getting it wrong is invisible until the unseal refuses — and because prose cannot be pinned by a test. Keeping the merge in deterministic Python is what lets the union, the idempotence, and the no-record case each have an assertion.
- **Pass a second list to the transfer role.** Hand `extract-transfer` the poll verdict beside the job record and let it subtract both. Rejected because it would force rewriting that role's hard rule — *"Never unseal against the selection as it was built — only against the selection as the job record says it was submitted, minus the plugin's `skipped_files`"* — at exactly the step where getting it wrong is the bug this decision fixes. The merge as chosen leaves that rule literally unchanged: the job record really does stay the one source, and it is now complete.
- **Relax `unseal.py`'s strict selection equality.** Tempting, because the refusal is what the operator sees. Rejected: the refusal is correct. The helper is being given the wrong list, not applying the wrong rule, and a validation that tolerates a missing file tolerates a truncated container too.
- **Make the widened `strict` conditional on the client asking for it.** The cleaner protocol shape — a client opts into packaging-time skips and knows what it is getting. Rejected because it is the Extractor's to offer, and this client must work against the build that already exists.
- **Probe production for the file's absence before unsealing.** Confirm each expected-but-missing file really is gone. Rejected as a second walk of production at the end of a run that already has the answer in a payload it threw away.

## Consequences

- **The unseal reconciles against every skip**, so a mid-run skip unseals successfully instead of returning `FAILED` after the whole download. That is the whole of the fix.
- **The job record has a second writer.** Its SHA256 is checked once, by the orchestrator, *before* the poll begins — which is why a record the poll rewrites breaks nothing. No step re-checks the pre-poll digest afterwards, and none may be added: `skills/clone/SKILL.md` §5 and `skills/pull/SKILL.md` §5 say so where the check is stated.
- **A merge that cannot be written is logged, never raised.** The verdict this poll reached is about the job; losing a `ready` over a local file would leave a finished extraction published on production with nobody closing it out. The unseal then fails loudly on the frozen list, which is the status quo this decision improves on rather than a new failure it introduces.
- **The Extractor's `API_VERSION` stays 7 and this client's verified ceiling stays 7.** Kntnt/kntnt-extractor#59 argues the integer must move to 8 on Extractor ADR-0018's second ground — already-shipped logic made unsafe undetectably. The condition is met and the ground is empty: that protection exists to reach clients already in the wild, and there are none ([ADR-0021](0021-verified-against-extractor-api-version-7.md) records the ceiling this leaves standing). No bump, no ceiling raise, no lockstep release.
- **The residual risk is ordering, and it is accepted deliberately.** With no version gate enforcing it, the discipline is: land this before production's Extractor is upgraded to the build with the widened `strict`. Upgrading first leaves a window in which a mid-run skip still aborts a finished extraction. The fix is a no-op against the current production Extractor, so there is no reason to wait — which is what makes the ordering cheap to honour rather than a constraint anyone is tempted to shortcut. Should this client ever acquire installs it does not control, that emptiness stops holding and the version gate is the thing to reach for.
- **`docs/implementation-notes.md`'s unseal contract is true rather than aspirational.** It already promised "the submitted selection minus any `skipped_files` the `201` or a later poll reported"; there is now a mechanism that makes the second half happen.
