# A configuration-file copy is excluded at any depth, except the variant catcher

The always-excluded set carries fifteen spellings of `wp-config.php` and one broad catcher for everything else shaped like it. Until now every one of the sixteen was anchored at the install root: `is_excluded` matched a file entry with no `/` of its own only against a path that also had none. That anchoring was [#36](https://github.com/Kntnt/kntnt-wp-skills/issues/36)'s, and it was justified in a code comment rather than here — *a same-named file nested deeper in the tree is ordinary content, not the configuration file, a leaked secret, or core.*

The Extractor answers the same question differently, and has since 0.3.0. `Restricted_Path::is_restricted()` takes `basename()` of the normalised path before matching the whole `wp-config` family against it, so a copy at any depth is refused; only the SQL-dump and key-material family is gated on the path being root-level. That is live in production now and is not part of any pending widening. The two lists therefore disagreed on four shapes this client would still ask for — `wp-content/uploads/wp-config.php`, `wp-content/backups/wp-config.php.bak`, `backups/wp-config.php~`, `wp-content/plugins/x/wp-config-local.php` — and the server refuses the **whole** `POST /extractions` when a selection names one, not just the offending entry.

Nothing has met this yet: neither production run has hit a restricted-path refusal at all. But any site carrying a copy of the configuration file under `wp-content/` — a backup plugin's staging copy, a duplicated install under a subdirectory, a developer's snapshot — meets it on the next clone whose scope includes that path.

The two readings are both defensible, which is why this is a decision and not a bug fix that needed no record. The Extractor takes the superset reading because it is the last party that can guarantee a site's secrets stay on the site. This client anchored at the root because dropping a nested file silently removes something the operator may legitimately have wanted in the copy — and [ADR-0024](0024-a-restricted-path-refusal-drops-the-named-paths-and-resubmits-once.md) explicitly permits the divergence, since this list is a pre-filter and not a contract.

## Decision

**The family splits in two, and the anchoring follows the name's ambiguity.**

Every entry whose basename can *only* ever name a copy of the configuration file is matched **anywhere in the tree**: the plain `wp-config.php`, the appended and tilde backups, the dot-prefixed configuration file with any suffix or none, Emacs' auto-save and lock files, and the reordered `wp-config.bak` / `.old` / `.orig` / `.save` names with or without a trailing `.php`. A file called `wp-config.php` under `wp-content/` is a configuration copy wherever it sits; it is never content, it carries the complete secret family in clear text exactly like the live file, and this client never asks for it.

The one broad variant catcher, `wp-config-*.php`, stays anchored at the **install root**. Its basename can legitimately belong to a file that is not a configuration copy at all — a plugin's `wp-config-loader.php`, a theme's `wp-config-local.php` — so a nested one is read as content and kept. The divergence from the server survives exactly there, and only there.

**The anchoring is expressed in the pattern, not in a second matcher branch.** The set already carries the convention: a `**/`-prefixed entry is matched against the basename at any depth, and an entry with no directory component is matched only at the install root. The `.env` family has used the first form since #36. This change moves fifteen entries from the second form to the first and adds no mechanism. Both matcher copies — `filter_manifest.py`'s and `baseline_diff.py`'s — inherit it from the one constant without either being edited, which is what `tests/test_exclusion_matching_consistency.py` exists to keep true.

**The `wp-config-sample.php` carve-out is not touched, and must not be.** It is an exact whole-path comparison, and it stays correct precisely *because* the variant catcher is the one entry left root-anchored: no `**/`-marked pattern in the family can match `wp-config-sample.php` at any depth, so a nested copy is kept without the carve-out ever being asked, and the root copy is kept by the carve-out as before. WordPress' own bundled template is therefore sent at the install root **and** wherever a theme or plugin ships a copy — matching the Extractor, whose own exception is a negative lookahead on the basename.

## Rejected alternatives

- **Match the whole family anywhere, the variant catcher included.** The simplest reading of "match the server", and wrong in two ways at once. A nested `wp-config-sample.php` would match the broad glob and would *not* be carved back out, because the carve-out compares the whole path — so this client would drop WordPress' own bundled template wherever a theme or plugin ships one, while the Extractor, whose exception is on the basename, would happily have accepted it. That makes the client stricter than the server on the one file the server explicitly protects. Widening the catcher and moving the carve-out to the basename in the same change would fix that, but it would still drop a legitimately-named nested file for no gain: the shapes that actually carry secrets are already closed by the fifteen.
- **Accept the divergence outright and change nothing.** Legitimate, and the honest default: ADR-0024 permits it by name, the handling at submission absorbs the refusal, and the cost is a wasted round trip rather than a dead run. It was rejected because the fifteen shapes are pure secret-bearing copies that cost nothing to exclude — no operator wants a nested `wp-config.php.bak` in the copy — so paying a resubmission for them buys nothing. This alternative is what survives for the sixteenth entry, where the file might genuinely be wanted.
- **Resolve symlinks to see whether a link's target is a configuration copy.** Out of scope by ADR-0024, which rules it out by name: this client walks a manifest the server produced and resolves nothing itself.

## Consequences

- **This contradicts part of #36's stated reasoning, deliberately.** For the fifteen unambiguous shapes, a nested same-named file is *not* ordinary content, and the in-file comments that said so are corrected rather than left to be re-derived. #36's anchoring survives for the sixteenth entry, and for the SQL-dump, key-material, and core-file families, whose root-only anchoring is unchanged and is correct on both sides.
- **A nested file genuinely named like a configuration copy is now dropped from the copy rather than failing the run.** That is the same trade ADR-0024 already makes for a refused path, with one difference: this one is not reported, because the pre-filter never asks for it and the server never names it. The shapes involved make that acceptable — a file called `wp-config.php.bak` three directories deep is a leaked secret, not a manuscript.
- **The gap narrows; it does not close, and nothing asserts that it has.** `wp-config-local.php` nested under a plugin is still sent and still refused by the Extractor, at the cost ADR-0024 bounds. No test compares this client's list to the server's — ADR-0024 forbids that by name, and this decision does not weaken it. The list remains a pre-filter on what this client asks for.
- **The order of landing is the harmless one.** The client stops asking for files the server already refuses; the server's behaviour is unchanged and predates this change by several releases.
