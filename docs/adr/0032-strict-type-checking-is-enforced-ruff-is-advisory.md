# Strict type checking is enforced; ruff is advisory

The Python module of the coding standard has required **"strict mode on new code"** since the standard was written, and named ruff as the project's linter and formatter. Neither claim was ever backed by anything: the repository carried no `pyproject.toml`, no `mypy.ini`, no `ruff.toml` and no CI, `pytest.ini` was its only tool configuration, and `CONTRIBUTING.md` named exactly one verification command — the test suite. A requirement nothing enforces is not a requirement; it is a sentence.

The bill came in three forms. Two strict-mode regressions landed unnoticed and had to be repaired as their own ticket (issue #71). Three independent verifiers ran a type checker of their own accord, found those regressions, and correctly declined to fail a ticket on a check the project does not run — so the finding cost three sessions and bought nothing. And thirty-three mentions of ruff accumulated across `plans/` — and not one of mypy — several carrying an explicit *"never `ruff check .`"* instruction to the executor, because a repository-wide run reports findings nobody configured and nobody owns. Every ticket in the queue paid for this again, one "pre-existing" argument at a time, in its own status row.

The two tools are not in the same position, and pretending they were is what made the standard unusable. A strict type run over the helper tree had **seven** findings, five of them a narrowing guard and a `bool(...)` away from clean. A bare `uvx ruff check` reports **90**; ruff's own stock default set, `E4,E7,E9,F`, reports **one**. So "does this pass mypy?" has an answer here and "does this pass ruff?" does not — the ruff number is a property of the invocation, not of the code, and no ruleset has been chosen.

## Decision

**A type error stops work from landing. A lint finding does not — yet.**

Strict type checking is a first-class verification step beside the test suite, documented in `CONTRIBUTING.md` as one command run from the repository root:

```
uv run --with mypy --with pynacl==1.5.0 mypy
```

Three things about that command are the decision rather than incidental:

- **Strict mode and the checked directories live in `pyproject.toml`**, not in the command. The command carries no flags of its own, so it reproduces the enforced result from the repository's own configuration and cannot be half-run by someone who forgot one. That file holds `[tool.mypy]` and nothing else — no `[project]`, no `[build-system]`: the helpers are standalone PEP 723 scripts provisioned by `uv` from their own inline metadata, and nothing here makes the repository an installable distribution or changes how a helper runs.
- **The one declared third-party dependency is resolved, never ignored.** Exactly one helper — `skills/clone/scripts/unseal.py` — declares a dependency, `pynacl==1.5.0`. With `nacl.bindings` invisible, mypy cannot see that an already-`bytes` value is `bytes` and reports a `no-any-return` that does not exist; `--ignore-missing-imports` therefore *manufactures* a finding while blinding the check at the only boundary a real one could hide behind. Provisioning the dependency the way the script itself does costs one `--with` and removes both problems. The pin is consequently written twice, and `skills/clone/scripts/unseal.py`'s PEP 723 header owns it: `tests/test_type_check_consistency.py` reads the header and holds every document quoting the command to it, so the copy can never drift away from the original.
- **Ruff's status is stated rather than implied.** It stays the chosen linter and formatter, and it stays unconfigured and advisory: a bare run's output is advice, not a verdict on a change, and nothing may be failed on it. That ends the day a ruleset is pinned, which is a taste decision with a real spread behind it and is deliberately left to the maintainer.

**What the check covers is the deterministic helper seam and only it** — `scripts`, `skills/clone/scripts`, `skills/mkwp/scripts`, exactly the three homes `docs/spec.md` § *The deterministic helper seam* names and exactly the three `pytest.ini` puts on the import path. `skills/build-ollie-site/scripts/` is outside it deliberately, and the configuration says so in its own text rather than leaving the exclusion as an omission a reader has to notice.

The residual risk of a directory list is that a helper home added later is silently unguarded. That is answered with a sentence in the configuration — adding a new helper home to the repository includes adding it to the list — and with a test binding the list to `pytest.ini`'s, rather than with a different configuration shape (see *Rejected alternatives*).

## Rejected alternatives

- **Leave the standard as it is and rely on reviewers.** The status quo, measured: two regressions landed, three verifiers duplicated the same discovery, and every ticket re-argued the same "pre-existing" point. A rule with no enforcement behind it costs more than no rule, because people act on it inconsistently and then argue about it.
- **Enforce ruff in the same breath.** Tempting — one ticket, both tools. It cannot be done honestly: the finding count is 1 or 90 depending on a ruleset nobody has chosen, so "enforce ruff" would mean choosing that ruleset in an implementation ticket. Honesty about ruff's status is what this decision owes it; enforcement waits for the choice.
- **`ignore_missing_imports = true`, so the configuration needs no dependency.** Cheaper to write and strictly worse: it invents the one finding it appears to avoid, and it turns every future missing import — including a genuinely wrong one — into silence at the boundary where types are least knowable.
- **Check the whole repository and exclude the exceptions.** The same list upside down, and larger: it pulls in `tests/`, taking the count from 7 to **154**. The standard's strict rule was written for the helper tree, and inverting the list would put the scope decision in a growing exclusion list instead of a stable inclusion one.
- **Include `skills/build-ollie-site/scripts/`.** Measured rather than assumed: it takes the check from 7 errors in 4 files to **34 in 8**. The extra 27 are not the shapes this work inventories — four `no-untyped-def`, nine `type-arg` on bare `dict`, and an `Unsupported operand type for unary -` — and clearing them means introducing TypedDicts or casts, which is a redesign rather than a type-level repair. Those five helpers are also written against a different baseline (`requires-python = ">=3.10"`, no `dependencies` key at all), and `docs/spec.md` already says in as many words that they are *not* the transfer engine's helper seam. Widening the check to reach them later is optional work; this decision does not create a debt.
- **Pin mypy's version in the documented command.** Principled — an unpinned checker can turn red with no code change — and rejected for consistency: `uv run --with pytest pytest` does not pin pytest either, and a version floating in one command while frozen in the one beside it is the kind of inconsistency nobody remembers the reason for. The exact-version rule in the standard governs a script's PEP 723 dependencies, which is why `pynacl` is pinned here and mypy is not. If a future mypy release does redden the seam, that is a repair like any other, and pinning both commands together is the change to make then.
- **Add CI to run the check.** Out of scope and not obviously wanted: this project has no CI at all, and the test suite has been a documented command since it was written. The gate is documented the same way, on the same footing, for the same reader — a contributor or an unattended agent at a terminal.
- **`# type: ignore` on the five findings.** Faster, and it defeats the purpose. The repairs are a narrowing guard on an optional HTTP response and a `bool(...)` around a comparison over `Any` — both type-level, neither changing a byte of runtime behaviour. `tests/test_type_check_consistency.py` pins the two suppressions that predate this decision and reddens on a new one, so silencing stops being the cheap route.

## Consequences

- **The seam is clean, so "pre-existing" stops being an argument.** `mypy` reports zero errors over 17 helper files. Any error a later reader sees belongs to the change in front of them.
- **`CONTRIBUTING.md`, `docs/spec.md` § *Testing Decisions*, `agents.d/coding-standard/python.md` and `plans/README.md` § *Gates* all name the same command**, and `tests/test_type_check_consistency.py` fails if any of them drifts from the pin the unseal helper declares. A verification step that four documents describe differently is a verification step nobody runs the same way twice.
- **The executor instruction in `plans/` is reconciled rather than reversed.** *"Never `ruff check .`"* was right and stays: ruff is advisory, so a repository-wide run is still noise. What changed is that the section saying so now also names the check that *is* enforced, and states which of the two is which. The verification tables inside completed plan files are records of what was run at the time, and are left standing.
- **Two helpers changed, at the type level only.** `skills/clone/scripts/poll_extraction.py` narrows the job-listing response before reading it — the `else:` arm of a `try` is where mypy cannot see that the failure path assigned `None`, so the arm becomes an explicit `is not None` guard, entered under exactly the same condition — and `skills/clone/scripts/resolve_plan.py` wraps a comparison over `dict[str, Any]` in `bool(...)`, which is a no-op at runtime because `==` already answers a real `bool`. Every helper keeps its original `requires-python` floor and its original `dependencies` list.
- **`uv` now creates a `.venv/` at the repository root** when either documented command runs, because a `pyproject.toml` is present. It is already gitignored, the test suite is unaffected (1360 passing, unchanged), and PEP 723 execution is unaffected — `uv run skills/clone/scripts/unseal.py` still resolves the inline dependency with a project file present. `uv` also warns that the workspace declares no `requires-python`; it defaults to `>=3.12`, which is the floor every checked helper declares anyway, and silencing the warning would mean adding the `[project]` table this decision deliberately omits.
- **A word of caution about the word.** This repository's glossary defines **gate** as a single yes/no prompt on a recommendation ([`CONTEXT.md`](../../CONTEXT.md)), and `docs/spec.md` makes that glossary binding in code, documentation, and dialogue. The CI sense of the word — a check that blocks a merge — is a different thing, and the surfaces this decision touches say *enforced* instead. Issue #74's own title uses "gate" in the CI sense; that is the issue's prose, not this project's vocabulary.
