# Close the exposure window on every failure path, not only the happy one

Both poll-owning subagents already shape their `FAILED` verdict for a cleanup the orchestrator was never told to perform. `agents/extract-transfer.md` returns an exhausted stall window as `FAILED` carrying the job id specifically "so the orchestrator can cancel the still-active job"; `agents/discovery-classify.md` says the same for the bootstrap loop, "so the orchestrator can consume or cancel the still-active job." Neither `skills/clone/SKILL.md` nor `skills/pull/SKILL.md` ever did it. `DELETE /extractions/{id}` appeared in each only at the *next* run's stranded-job sweep and at §7's prohibition against using it as the happy-path close — never as a step that runs after a `FAILED` return in the run that just failed.

Three leaks followed from that gap. First, an unseal that fails after a complete download leaves the production artifact published with a local copy already in hand to replace it — nothing consumed it. Second, an exhausted stall window leaves the job active on production, holding the plugin's one-active-job rule against the next attempt, and — once that job later fails server-side — even the next run's sweep can no longer see it, because `GET /extractions` lists only non-terminal jobs. Third, a failed bootstrap deliberately leaves a cleartext dump of real user and, when a recognised CRM was carried, subscriber rows on local disk for diagnosis — a genuine and intentional exception — but nothing then told the operator it existed or ever removed it, so the exception had no expiry.

The first two leaks leave sealed production data published on a live client site until TTL, precisely the window §7 exists to keep to minutes. The third leaves real personal data in cleartext on local disk with nothing scheduled to remove it.

## Decision

Every submitted job is accounted for before a run stops — by cancel, by consume, or by an explicit reported decision — never by silence. A new *Closing out a failed phase* subsection in both SKILLs, reached from any `FAILED` subagent return or any orchestrator-initiated abort after a job was submitted, specifies four cases (the fourth added 2026-08-20 — see the locked-consume amendment):

1. **Never reached `ready`** — cancel with `DELETE /extractions/{id}`. No artifact exists to preserve, and the job otherwise blocks the next attempt.
2. **Reached `ready`, downloaded, but the unseal failed** — consume with `POST /extractions/{id}/consume`. The download precedes the unseal, so a complete local copy already exists; consuming destroys nothing not already on this machine.
3. **Reached `ready` but the download failed or never ran** — report only. The production artifact may be the only copy of a multi-hour extraction. Offer consuming it as its own accept-or-override gate; under `--yes`, with no operator present to own that choice, do not consume — print the information for the record instead.
4. **Reached `ready`, downloaded and unsealed, but every consume was refused `409 kntnt_extractor_locked`** — report only, and report the transfer as complete. The bounded retry below has already been spent; nothing further is attempted, and the artifact is left to its TTL and the next run's sweep.

The close-out is best-effort and never masks the original failure: a close-out call that itself fails is reported alongside the original cause, and the run still stops on the original cause. The diagnostic bootstrap dump exception in `agents/discovery-classify.md` is kept, not reversed, and bounded instead: the orchestrator is now required to report its exact path and delete it before the run ends, defaulting to delete, with an operator override to keep it for diagnosis; under `--yes` it is deleted without asking and the record says so. The subagents' evidence blocks are extended so the close-out has what it needs without re-deriving it: `extract-transfer` now always returns the job id on `FAILED`, plus a `failure_phase` naming which case applies and the downloaded container's path when a download completed; `discovery-classify` now returns the bootstrap job's id and last observed state, plus the cleartext dump's path whenever `bootstrap_artifacts_deleted` is `false`.

Both SKILLs' §1.3 stranded-job sweep additionally calls `GET /extractions?state=all` — unconditionally, with no version check and no `honours` read — since WordPress silently ignores a query parameter a route has never registered: against production's current 0.4.0 Extractor this call is answered exactly as the plain listing and costs nothing; against an Extractor that has landed the parameter (its own plan 013) it additionally admits the caller's own terminal jobs, reported but never acted on, since a terminal job the sweep did not create this run may be another operator's or a deliberately retained diagnostic.

## Rejected alternatives

- **Always consume on failure.** Destroys a completed, possibly multi-hour extraction to save minutes of a TTL-bounded exposure window whenever the download itself is what failed — the worse trade of the two available.
- **Always leave it to TTL.** The status quo. It leaves sealed production data on a live client site for the whole TTL while the operator is told nothing, and it leaves a job wedged against the one-active-job rule until the plugin's own watchdog clears it.
- **Delete the diagnostic bootstrap dump unconditionally.** The dump is genuinely useful on exactly the failure path this plan's field evidence shows is about to be exercised. Bounding and reporting it preserves that value without leaving it unaccounted for.

## Consequences

- A close-out failure never becomes the headline: the run's stop reason is always the original cause, with any close-out trouble reported alongside it.
- §1.3's stranded-job sweep and the plugin's TTL remain the only backstop for a run that dies outright — a crashed session or a killed terminal cannot run a close-out at all. That is inherent, not a gap this decision leaves open.
- Once the Extractor's plan 013 lands broadly (per-job tick locks on `consume`/`cancel`, sweep reclamation of an orphaned served artifact), leaks 1 and 2 become belt-and-braces rather than the primary mechanism — the same relationship §7's explicit consume already has with TTL. That is a reason to keep this client-side close-out, not to remove it: closing the window in seconds from the client is worth having even once the server would close it eventually.
- Those same per-job tick locks are what the fourth case exists for: `consume` now answers `409 kntnt_extractor_locked` when the lock is held, and a client that closes the window in seconds is precisely the client that can be refused. See the locked-consume amendment below.
- No new consistency suite pins the first three cases across all four surfaces the way `tests/test_poll_discipline_consistency.py` pins the poll discipline. That document earned its canonical status only after its wording had drifted across four surfaces in the field; pre-building the same machinery for a rule stated once, not yet observed to drift, would be the premature version of the same idea. Noted as a follow-up candidate if drift is later observed. The fourth case is the exception and has `tests/test_locked_consume_retry_consistency.py` from the start, because its bound is a number stated on three surfaces at once — the shape that has drifted here before.

## Amendment (2026-08-20): the job's own state outranks the verdict that reached the close-out ([#53](https://github.com/Kntnt/kntnt-wp-skills/issues/53))

Two production runs exercised this decision for real, and both exposed the same defect in it — not in what the close-out cases do, but in how one of them is reached. The close-out is entered from a `FAILED` return, and the engine reads a result that arrives without its evidence block as `FAILED`. Case 1 then maps an exhausted stall window to `DELETE /extractions/{id}`. Chained, those three rules turn a subagent that returned **nothing at all** — no verdict, no evidence, no claim about the job whatsoever — into a cancel of the job it was watching. The least informative return possible was being read as the most specific case.

On 2026-08-19 `extract-transfer` returned with no evidence block after two and a half hours. The job was `running` with `chunks_done` climbing throughout and went on to complete all 48,578 files. The only thing between that run and a `DELETE` was the orchestrator querying the job by hand, on its own initiative and contrary to the written close-out. The same shape occurred on 2026-08-18.

**The ordering is therefore part of this decision.** On any `FAILED` verdict, and equally on any absent or malformed one, the close-out issues a single `GET /extractions/{id}` before selecting a case at all. The job's own reported state outranks the subagent's claim about it: a job reporting `running` with progress advanced since the last observation selects no close-out case — the run resumes polling it instead. An absent verdict is explicitly not evidence of an exhausted stall window. The subagent's own role file now scopes its verdict to match: `FAILED` binds the role's work, never the job's state, and the orchestrator resolves the difference by asking the server.

Nothing about what the close-out cases do changes. The re-query gates the cancelling branch and only that: case 2's `consume` after a failed unseal is reached on a download that already succeeded, and holding it back would widen the very exposure window this decision exists to close. Cases 3 and 4 are report-only either way. The cost is one `GET` before every failure close-out, which is the intended price.

This also revises the last consequence above. `tests/test_close_out_state_precedence.py` now pins the ordering, the absent-verdict coverage, and the two SKILLs' identical wording of the rule — the drift this note said would justify such a suite arrived as a defect rather than as divergent prose. The first three cases still have no consistency suite of their own, and that remains a follow-up candidate rather than a gap.

The general shape, stated once in `docs/spec.md` rather than re-derived per phase: where a local claim and a remote authority disagree about remote state, the remote authority wins.

## Amendment (2026-08-20): a locked consume is retried, not failed ([#54](https://github.com/Kntnt/kntnt-wp-skills/issues/54))

The Extractor makes both purging routes take the per-job tick lock, because either could otherwise delete the directory a live build was still writing into, and answers `409 kntnt_extractor_locked` when it cannot take it — with "the caller simply retries" as the intended handling. This client had no handling for that code, and the rule above that a job never consumed on the happy path is always `FAILED` turned a narrow lock contention into a failed verdict on a finished multi-hour extraction. Observed on a production run, not hypothesised.

**The consume is now retried up to five times, 10 seconds apart, and only the exhausted window fails.** The bound is derived rather than picked (rule R4): the longest any actor holds a job's lock is one `tick_budget` — 15 s by default, Extractor ADR-0010 — plus the one chunk that may overrun that deadline, and the TTL sweep holds it only across a single job's purge, so six attempts across roughly 50 s cover more than three default budgets. The residual risk the bound accepts is named rather than hidden: a site that has raised `tick_budget` past that window can still exhaust the retries, and lands in the fourth close-out case.

**The data is never at risk on this path, and the surfaces say so.** The download and the unseal both precede the consume, so an exhausted window forfeits the run's verdict and the immediate close of the exposure window — never the copy. That is why the fourth case reports the transfer as complete and leaves the artifact to its TTL rather than reporting a failed transfer, and why the `extract-transfer` role reports `unsealed_consume_locked` as its own `failure_phase` instead of folding into `downloaded_unseal_failed`.

Not widened to `DELETE /extractions/{id}` when this amendment was written, and named a follow-up rather than an oversight. That follow-up was taken on 2026-08-21 for the close-out's own case-1 cancel — see the locked-cancel amendment below. §1.3's sweep keeps its cancel unretried: a failed cancel there is already handled as a reportable condition rather than a run-ending one, and changing it changes sweep semantics rather than close-out semantics. If the Extractor ever makes the lock wait rather than refuse, both retries should be deleted rather than kept as harmless belt-and-braces — silent attempts against a route that no longer refuses would hide a real error.

## Amendment (2026-08-21): the close-out establishes the phase itself, and a reported one is only a hint ([#65](https://github.com/Kntnt/kntnt-wp-skills/issues/65))

The first amendment stopped an absent verdict being read as case 1. It left a hole one step further in, which the wave-level verification of that work found rather than any single ticket's own: cases 2, 3 and 4 are all `ready` jobs, and the only thing telling them apart was the `failure_phase` the role reported. An absent verdict carries no `failure_phase` — that is what makes it absent — so an absent verdict against a job the re-query answers `ready` matched no case at all. The same is true of a well-formed `FAILED` from `discovery-classify` or from `extract-submit`: neither evidence block has ever had the field. Three routes into this close-out therefore reached a state it had no instruction for, on a job that may hold hours of extraction. Nothing was at risk — the re-query is what stops silence cancelling a live job — but an undefined state on a destructive path is a defect whether or not it has bitten yet.

**The case is derived, not read off a claim.** Two authorities settle it: the job's own state, from the single `GET /extractions/{id}` the first amendment established, and this machine's own state — what the run's scratchpad holds. Where a `failure_phase` was reported it is **a hint, never the selector**; the vocabulary is kept, because it is useful corroboration and it belongs in the run record, but where the hint and the derived state disagree the derived state wins. This is the same precedence as the first amendment, applied one step further: a remote authority outranks a local claim about remote state, and the machine's own state outranks a session's claim about the machine. The alternative — adding `failure_phase` to the other two roles — was considered and rejected: the field can be absent for reasons the close-out can never detect, so a close-out that trusts it is undefined again the next time a session returns without one.

**A probe needs a name as well as a directory, so the artifacts got fixed ones.** The main container had no filename fixed anywhere: `extract-transfer` said only "into `<scratchpad_dir>`". It now downloads to `<scratchpad_dir>/extract.container.part` and renames to `<scratchpad_dir>/extract.container` only after the transfer exits cleanly, which makes the final name's existence the answer to *was a sealed container downloaded?* — `curl -C -` leaves a partial file behind on a failed transfer, and a truncated container answering to the whole one's name would select the consume that destroys the only complete copy. The unseal's outputs are `<scratchpad_dir>/extract.sql` and `<scratchpad_dir>/extract-files/` for the same reason. The bootstrap job keeps the same shape inside `discovery-classify`'s own per-run working directory, which is where that role has always written it; both SKILLs' §3 said the scratchpad root and were wrong, so the probe globs `<scratchpad>/discovery-classify-*/` and every surface now names one layout instead of three.

**Cases 2 and 4 are one row, distinguished by outcome rather than by state.** A `ready` job that was downloaded and unsealed presents identically on disk whether the consume was never attempted or was attempted and refused six times, and the field that told them apart is exactly the one demoted here. So the close-out stops trying to detect the difference: where the job is `ready` and the container is on disk, it attempts the consume. Success is case 2; refusal through the whole bounded retry window *is* case 4. The risk is asymmetric, which makes this an easy call rather than a balanced one — an unnecessary consume costs the retry window and nothing else, since the download and the unseal both precede it, while a needed one not attempted leaves the sealed artifact on a live client site until its TTL, the exposure window this decision exists to close. Neither case's action changes; only how the close-out arrives at it.

**Every combination has a stated outcome, including the three that are not a case.** An advancing `queued`/`running` job selects no case and the run resumes polling it (the first amendment's outcome, unchanged). An already-`consumed` job selects no case because the artifact is gone and there is nothing left to close — a reachable state, since a role can consume and then return without an evidence block, and one no previous case covered. A re-query that could not be answered at all selects no case and acts on nothing, reporting the job id and that its state is unknown: absence of information must never select the destructive branch, which is the whole of the first amendment's rule. The two SKILLs carry the mapping as a table so completeness is visible rather than inferred, and `tests/test_close_out_state_precedence.py` is extended to pin the derivation, the probe's fixed paths, every state's outcome, and — the criterion the first amendment's suite could not check — the two SKILLs' *whole* subsection being identical rather than only its re-query paragraph.

## Amendment (2026-08-21): a locked cancel is retried too, and an exhausted window is not a failure ([#68](https://github.com/Kntnt/kntnt-wp-skills/issues/68))

The follow-up the amendment above named is taken here. The Extractor takes the same per-job tick lock in its `DELETE` handler that it takes in the consume handler and refuses with the same `409 kntnt_extractor_locked`, with the same recorded intent — "the caller simply retries" — so case 1 above was issuing a call this client had no handling for. The plugin's own source notes that the cancel is the caller *most* likely to race a live tick, because it reaches a job in any state the run owns, `queued` and `running` included, while the consume only ever reaches a job that has already gone `ready`.

**Case 1's cancel is retried on the consume's schedule — up to five times, 10 seconds apart — and the derivation is copied with it.** The longest any actor holds a job's lock is one `tick_budget`, 15 s by default (Extractor ADR-0010), plus the single chunk that may overrun it, so six attempts across roughly 50 s cover more than three default budgets. One schedule stated twice is a schedule; two schedules would be a coin toss, which is why the numbers are the consume's rather than tuned for this route. **The cover the same numbers buy is weaker here, and the surfaces say so rather than borrowing the consume's confidence:** a `ready` job races a tick only in the narrow window between that tick publishing the artifact and releasing its own lock, while a `queued` or `running` job's ticks keep retaking it. Six attempts therefore bound what is attempted; they do not guarantee the cancel. The weaker cover is accepted rather than answered with a longer window, because an unbounded retry against a live client site is the thing the bound exists to refuse.

**An exhausted window is reported, never run-ending.** The close-out is best-effort and a cleanup failure never becomes the headline, so the report names the job id, says the job is still standing on production, and says the plugin's TTL — and the next run's stranded-job sweep where the job is still non-terminal — will reclaim it; the run then stops on its original cause. That qualification is not hedging: case 1 is also entered on a `failed` job, which is terminal, and §1.3's sweep lists only non-terminal jobs, so the TTL is the only reclaimer for that sub-case.

What an exhausted window costs is bounded but not merely bookkeeping, and it is larger than at the consume. Case 1 is entered on a job that has *not* reached `ready`, so a refused cancel leaves that job's tick running: the job may go on to complete and publish a sealed artifact on the live client site, served until its TTL — the exposure window this decision exists to close, reached through the door the amendment above left open. No data is lost on either side of the refusal.

`429` is not retried here, exactly as it is not retried at the consume: a different code with a different meaning and its own hard stop at submission. Every other non-2xx keeps the handling it had. `tests/test_locked_cancel_retry_consistency.py` is the anti-drift binding — a sibling of the consume's suite rather than an extension of it, because the surfaces differ: the consume's schedule is stated on the `extract-transfer` role as well, while the cancel is issued only from case 1, which lives in the two SKILLs alone — `docs/spec.md` and `CONTEXT.md` carry it beside the consume's, as they already carry that one.
