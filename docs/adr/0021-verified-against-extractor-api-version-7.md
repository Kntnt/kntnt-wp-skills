# The verified Extractor API-version ceiling is raised from 6 to 7, on evidence rather than on the number alone

`VERIFIED_CEILING` (`tests/test_api_version_ceiling_consistency.py`) exists because a version number alone cannot be trusted to mean "this client understands the artifact it is about to reassemble". Extractor API version 5 is the proof: it turned one sealed segment per table into one *or more*, and a client built against the older shape kept only each table's last slice — every other slice lost, no error raised on either side, both repositories' suites green throughout. The ceiling is this repository's declaration, checked by a suite that refuses to let it drift silently, that a specific higher version has actually been examined against that hazard before a `GET /status` reporting it is allowed to proceed rather than stop for the operator.

The Extractor's `Status_Controller::API_VERSION` moved from 6 to 7 in commit `7dc242047bbb60df8fd5a90f822005b0046c984b`, for the `GET /environment` define-disclosure allow-list (Extractor ADR-0018). Reading that ADR directly, this bump is not a shape claim: ADR-0018 states outright that, under Extractor ADR-0017's rule — `api_version` bounds only the artifact's byte layout, segment framing, segments-per-resource, sealed index, and reassembly order, and every other caller-visible change ships as a `honours` capability instead — the define-disclosure change "would ordinarily be a `honours` entry instead". It bumps anyway, as a named, deliberate exception: an already-shipped, unmodified `kntnt-wp-skills` client classifies a `null`-valued define by name alone and would port a newly-withheld one into a local `wp-config.php` as `define('X', null)`, silently defeating whatever fallback the owning plugin runs. Plan 001 (merged as `66e42e9`) is what makes this client correct against that allow-list, and is why this ceiling raise could not happen before it landed.

Two changes this plan expected to also ride the bump did not, once checked against the Extractor repository directly rather than against this plan's advance summary. The `honours` capability list itself (Extractor plan 014) ships the member named `honours`, not `capabilities` — that name was already taken by the caller's own WordPress capabilities on the same endpoint — and Extractor ADR-0017 states plainly that adding a name to `honours` never moves `api_version`; it did not ride this or any bump. A `state` query parameter on `GET /extractions` (Extractor plan 013) has not landed at all, and its own text commits it to the same capability-list mechanism rather than a version bump whenever it does.

## The verification, not the edit

The six-literal edit this raise makes is trivial; the plan that authorised it says so directly, and states that skipping the verification and doing the edit anyway "launders an unverified contract through a test that reads as verification." What was actually checked, and is recorded in full in `plans/004-raise-the-verified-api-version-ceiling-to-7.md`'s own `## Verification record`:

- Extractor ADR-0018 and ADR-0017, read for what each change actually claims about the artifact.
- The Extractor's normative `docs/container-format.md` (its plan 009), whose §8 states `FORMAT_VERSION` is currently `1` and is unmoved by this bump — `FORMAT_VERSION` moving always accompanies an `api_version` move, but the reverse does not hold in general, and this bump is exactly the case where it does not.
- Every commit in the Extractor repository touching `classes/Crypto/` or `classes/Artifact_Builder.php` since its last tag (`v0.5.1`), read individually rather than trusted from the changelog's own framing: none changes a byte that reaches the sealed container, only how those bytes are written (fewer redundant filesystem round trips, no `php://temp` spill, deferred sidecar cleanup).
- This repository's own reassembly contract, `scripts/unseal.py` and `docs/implementation-notes.md`'s *Container format* section, confirmed unaffected and requiring no change.

No version-7 container was unsealed. A local DDEV round trip against a real version-7 build was the plan's own named strongest check, and was deliberately not attempted here: it would have meant standing up infrastructure for a check that source inspection from three independent angles already answers, and the operator exercises a real round trip at release time regardless. This raise therefore rests on **source inspection**, not on an artifact actually observed. That is a materially weaker claim than "a version-7 container unsealed correctly", and the record says so in those words rather than implying otherwise.

## Consequences

- `VERIFIED_CEILING` is `7`; `FLOOR` is unchanged at `2`. Every pinning surface (`skills/clone/SKILL.md`, `skills/pull/SKILL.md`, `docs/spec.md`, `docs/implementation-notes.md`) states both bounds, enforced by `tests/test_api_version_ceiling_consistency.py`.
- `scripts/unseal.py` is unchanged. No evidence gathered here calls for a change to it, and none should be made speculatively — a reader written against a shape that has not actually moved is a reader that has not been tested against anything new.
- **The raise is a declaration of having checked, not a declaration of certainty.** The correct response to a future version this repository cannot examine with the same rigour — no ADR naming the artifact question, no normative format document, an artifact-writing history that cannot be read commit-by-commit — is to leave the ceiling exactly where it is and let the client stop for the operator. That stop is the designed behaviour this whole mechanism exists to produce, not a failure of it.
- This raise depended on plan 001 landing first, and on Extractor plan 008 having landed; it did not depend on, and does not claim anything about, Extractor plans 013 or 014, whose artifact impact is separately recorded as none in the verification record above.
