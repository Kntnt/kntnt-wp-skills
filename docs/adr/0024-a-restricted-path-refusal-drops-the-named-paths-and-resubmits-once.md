# A restricted-path refusal drops the named paths and resubmits once

The Extractor refuses a `POST /extractions` whose selection names a path its own restricted-path policy covers: `422` with `code == "kntnt_extractor_restricted_path"`, every offender in `data.paths`, and the **whole create rejected** rather than the offending file quietly dropped. That is the right server behaviour — the plugin is the last party that can guarantee a site's secrets stay on the site, and it does not trust the caller to have filtered. It is also a behaviour this client had no answer for: before this decision, `kntnt_extractor_restricted_path` appeared nowhere in this repository's runtime surface at all, and the submission step described `422` only as "malformed or overlapping selection" and treated it as a hard stop.

The failure that follows is not hypothetical. A site carries a `wp-config.old` left behind by a manual edit, or an `id_ed25519` at the install root; this client's exclusion patterns — a pre-filter written against an older reading of the server's policy — do not recognise the shape and include it in `files`; the server rejects the entire create; and the operator meets an unrecognised error code at the exact step that was supposed to start a multi-hour transfer. A clone that worked yesterday fails today, and nothing in the run explains why.

## Decision

A `422` whose `code` is `kntnt_extractor_restricted_path` is not a hard stop on its first occurrence. The client reports every path in `data.paths` to the operator with the reason, drops exactly those paths from the selection's `files`, and resubmits the create **once**. The refused request created no job, so the resubmission starts nothing twice, and the corrected selection becomes the submitted one — the unseal reconciles against it, not against the list the server refused. A second `kntnt_extractor_restricted_path` on the resubmission **is** a hard stop, returning `FAILED` with both bodies. The dropped paths ride the `extract-transfer` role's evidence block as `restricted_paths`, beside the vanished-file `skipped_files`, so the run report can name what the copy does not contain.

**The bound is one retry, not a loop, by construction.** The server names *every* offender in one response, so a single corrected resubmission is sufficient whenever the two sides agree about what was named. A second refusal therefore means they do not agree — a normalisation difference, a symlink resolved server-side, a path spelled differently on the two sides — and no number of further attempts fixes a disagreement about naming. Retrying past that point would loop against a live production site for as long as the operator let it.

**The client's exclusion patterns are a pre-filter, not a contract, and must not become one.** They exist so this client does not *ask* for files it never wanted; they are not a claim about what the server will refuse. The Extractor's own `docs/define-disclosure.md` sets the precedent for the sibling protocol: server-side policy may change between releases without an `api_version` bump, and a reader must not hard-code or assert it. The same holds here. This repository therefore mirrors the server's widened family as a best effort — Emacs' auto-save and lock files beside `wp-config.php`, the reordered `wp-config.bak` / `.old` / `.orig` / `.save` names with or without a trailing `.php`, and OpenSSH's full set of default key basenames — and **no test asserts that the two lists are equal**. The mirror is allowed to go stale again; that is why the handling above exists, and the handling, not the currency of the list, is what makes staleness survivable.

## Rejected alternatives

- **Report clearly and hard-stop.** Defensible, cheaper, and genuinely close: the operator would at least be told which path was refused instead of meeting a bare error code. It was rejected because the operator's only recovery from it is to hand-edit a selection of tens of thousands of paths, at the start of a transfer they have already waited for a discovery pass to reach. If the single resubmission ever proves troublesome — a server that refuses non-deterministically, a paths list the client cannot match against its own spelling — this is the option to fall back to, and falling back to it is a small change.
- **Retry until the refusals stop.** Unbounded work against production for a condition that, past the first correction, is a disagreement rather than a backlog. See the bound above.
- **Assert the client's pattern list equals the server's, with a test that fails when they drift.** A false contract across two independently released repositories, and one that would redden this repository's suite for a change made in the other one. The lists answer different questions and are permitted to differ.

## Consequences

- **This decision strengthens no security guarantee, and does not claim to.** The guarantee that a site's secrets stay on the site is enforced server-side precisely so that no client's correctness is load-bearing for it. What changes here is availability and diagnosability for the one production consumer of this API: a transfer that used to die at submission now completes, minus files it should never have asked for, and says which ones.
- The widened patterns exclude files this client had no business transferring in the first place, so landing them ahead of the server's own widening is harmless and can be done early. The two must not land in the other order: the server refusing selections this client still builds, with no handling on this side, is exactly the break described above.
- A file wrongly named like a restricted shape — an author's `wp-config.old` kept deliberately as content, say — is now dropped from the copy rather than failing the run. That is the same trade `strict: false` already makes for vanished files, and it is bounded the same way: the drop is reported by name, never silent.
- Nothing local resolves symlinks to see whether a link's *target* is restricted. The client walks a manifest the server produced and resolves nothing itself; that check belongs server-side, where the Extractor is adding it. Wanting it client-side later would be a new decision, not an extension of this one.
